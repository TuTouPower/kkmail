# Task spec

## 背景

用户打开含外链图片的 HTML 邮件时，点击「仅此邮件允许加载」后图片仍停留在占位状态；刷新网页后放行状态完全丢失，再次出现拦截提示；也无法将某个发件人的邮件图片设置为长期允许。`p066` 已核实代码事实：放行状态仅存于 `MessageReader` 组件局部的单值 `useState`，既未持久化也未集合化；邮件正文 iframe 的 React key 不包含放行状态；后端当前没有任何远程图片放行记录。放行后正文是否真的未重试请求仍缺真实浏览器证据，现有 scratch 测试反而观察到 `srcdoc` 更新会触发新的图片请求；因此本 task 要求实施前用真实浏览器与真实邮件复现，再决定强制重建是否为必要修复或仅作防御性加固，避免把假设当根因。用户已确认：单封邮件放行与发件人放行两类状态都必须入库持久化。

## 契约区

### 范围

- 服务端持久化两类远程图片放行：按邮件、按发件人地址。发件人白名单为服务端全局作用域（跨账号共享），以服务端解析出的结构化 `from_address` 为准；写入、命中与移除统一做去首尾空白加小写规范化后精确匹配，重复写入只保留一条记录。
- 放行请求必须由服务端确认持久化成功后才放开图片加载；失败时保持拦截、提示错误并允许重试。
- 邮件详情返回「当前邮件是否已放行」；阅读器以此决定是否加载远程图片与是否展示拦截提示。
- 拦截提示提供「仅此邮件允许加载」与「总是允许来自此发件人的图片」两个操作；后者仅在发件人地址可解析为有效邮箱时提供。
- 放行成功后，当前阅读器立即以全新邮件正文文档重新渲染并开始加载图片，无需用户手动刷新页面。
- 设置页提供已允许发件人的查看与移除；移除后当前会话重新打开相关邮件即恢复拦截，不依赖缓存自然过期。
- 数据库迁移、后端接口与前端 OpenAPI 契约同步更新。

### 非范围

- `cid:` 内联附件图片地址解析与替换（另见 `p067`）。
- 阅读器单信深色覆盖 `viewModeOverride` 的生命周期调整（另见 `p068`）。
- 域名级、图片托管域名级或全局「总是加载所有图片」白名单。
- 单封邮件放行的撤销界面；该记录仅在邮件删除时级联清理，发件人白名单可单独移除。
- 修改 DOMPurify 清洗规则、CSP 指令集合或 iframe `sandbox` 安全基线。
- 浏览器本地存储作为放行权威来源；本 task 明确改为服务端持久化。

- [ ] AC-001：默认情况下，含 http(s) 远程图片的 HTML 邮件不加载图片并显示拦截提示；不含远程图片的 HTML 邮件不显示提示；纯文本邮件不显示提示。
- [ ] AC-002：点击「仅此邮件允许加载」后，当前邮件无需手动刷新即开始加载远程图片，拦截提示消失。
- [ ] AC-003：单封邮件放行后，刷新网页、清空浏览器站点数据或在新的浏览器会话中重新打开该邮件，图片仍直接加载且不显示拦截提示。
- [ ] AC-004：单封邮件放行仅作用于该邮件；切换到其他未放行邮件仍拦截，切回已放行邮件仍直接加载。
- [ ] AC-005：点击「总是允许来自此发件人的图片」后，当前邮件立即加载；同一发件人地址（大小写与首尾空白归一化后相同）的其他邮件在刷新或新浏览器会话中不再显示拦截提示并直接加载图片。
- [ ] AC-006：发件人放行不影响其他发件人的邮件；发件人地址为空或不能解析为有效邮箱时，界面不提供该操作，服务端也拒绝保存该地址。
- [ ] AC-007：设置页展示已允许的发件人地址并支持移除；移除后，当前会话重新打开该发件人的已缓存邮件即恢复拦截，无需等待缓存过期；该邮件若另有单封放行记录则仍加载。
- [ ] AC-008：删除邮件后，其单封邮件放行记录随数据库级联清理且不残留；删除邮件不影响发件人放行记录。
- [ ] AC-009：放行状态变化不改变安全基线：未放行邮件的 CSP 图片源仍仅允许 `data:` 与 `cid:`，iframe `sandbox` 不含 `allow-scripts` 或 `allow-same-origin`，DOMPurify 过滤规则不变。
- [ ] AC-010：服务端对不存在的邮件返回未找到；重复放行同一邮件或同一发件人为幂等成功；Cookie 会话写请求沿用现有 CSRF 校验，合法 API Key 保持现有免 CSRF 行为。
- [ ] AC-011：邮件详情返回的放行标志与实际记录一致：单封邮件记录命中或发件人记录命中任一成立即为已放行，两者均不命中即为未放行。
- [ ] AC-012：发件人白名单跨全部收件账号生效：同一地址在任一账号的邮件中放行后，其他账号中来自该地址的邮件同样直接加载；大小写或首尾空白不同的同一地址被视为同一条记录，移除时同样命中且列表中不出现重复项。
- [ ] AC-013：放行请求在服务端确认保存前不发起远程图片请求；请求失败时保持拦截并显示错误提示，用户可重试；请求未完成时切换到其他邮件，不把放行状态带到其他邮件。

- 来源：`p066`（2026-10-30 核实：`MessageReader` 使用组件局部单值 `useState`，iframe key 未含放行状态，后端无放行存储；用户确认两类放行均入库）
- 创建前审阅：Codex `gpt-6.1-sol` 结论 `CHANGES_REQUIRED`；已按 findings 补发件人作用域与规范化、失败分支、缓存撤销与真实浏览器验证。`cid:` 与 `viewModeOverride` 分别登记为 `p067`、`p068`。

### 有意不测

- 第三方广告拦截插件对图片的拦截：不受应用控制，使用本地测试图片服务器验证应用自身行为。
- `cid:` 内联图片显示：不在本 task 范围，见 `p067`。
- 域名级与全局放行：未定义产品语义，本 task 不覆盖。
- `viewModeOverride` 生命周期：不在本 task 范围，见 `p068`。

### 测试策略

- 后端 PostgreSQL 集成测试：两类放行记录的写入、幂等、大小写与空白规范化、跨账号全局命中、详情标志计算、非法发件人拒绝、邮件删除级联与发件人白名单独立保留；迁移升级与降级。
- 后端 API 契约测试：新接口状态码与 OpenAPI 生成一致性；无认证写请求拒绝，Cookie 会话缺失或错误 CSRF 拒绝，合法 API Key 保持免 CSRF。
- 前端组件测试：默认拦截；点击单封放行后正文节点重建且 CSP 放开；详情返回已放行时无提示条并直接放开；发件人放行与非法地址隐藏操作；纯文本与无远程图片邮件不出现提示；设置页列表与移除；移除后重新打开缓存邮件恢复拦截；放行请求失败或无响应时保持拦截且切换邮件不串状态。
- Playwright E2E：用可控图片服务器统计请求并确认图片成功解码，验证点击前无请求、点击后发起请求且可见，刷新后不重复拦截；发件人白名单对同发件人第二封邮件生效；失败响应不产生图片请求。
- 真实浏览器复核：实施前用真实 Chromium 与真实邮件样本复现“放行后不重载”，记录请求与解码结果；若复现显示 `srcdoc` 更新已能触发请求，继续定位 `cid:`、混合内容或 URL 重写等真实原因，不直接以 remount 收尾。

### 风险与回退

- 风险：已有用户此前在浏览器会话内临时放行的邮件在本变更后需要重新放行一次；属于预期的语义升级。
- 风险：根因假设不成立；若真实浏览器复现显示就地更新已能重试请求，强制重建只作为防御性加固，必须继续定位 `cid:`、混合内容或 URL 重写等真实原因。
- 风险：发件人地址规范化（大小写、空白、损坏报头）与前端展示不一致，导致白名单看似不生效；以统一规范化函数与跨层测试收敛。
- 风险：撤销白名单后未使已缓存详情失效，staleTime 内继续放行；以当前会话重新打开缓存邮件的测试覆盖。
- 风险：放行 API 尚未确认持久化就乐观放开图片，失败后远程请求已泄露访问事实；以失败分支的请求计数测试覆盖。
- 回退：撤销发布后执行迁移降级删除两张新增表即可；不改动既有表与列，无既有数据迁移。

### 依赖与约束

- 需要新增 Alembic 迁移与重新生成 OpenAPI TypeScript 契约。
- 不引入新的第三方依赖；沿用现有认证、CSRF 与 PostgreSQL 事务设施。
- 放行记录属于隐私边界变更：只有用户显式操作且服务端持久化成功后才写入并放开图片，默认拦截行为与 CSP/sandbox 基线不得放宽。
