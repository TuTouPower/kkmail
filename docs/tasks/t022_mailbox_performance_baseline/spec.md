# Task spec

## 背景

现有分页、搜索及同步测试验证正确性，但未见可重放的大邮箱延迟、内存、数据库空间和磁盘占用基线。需要先测量真实成本，再决定优化，避免凭感觉设置跨机器耗时阈值。

## 契约区

### 范围

- 在 tests/ 或 scripts/ 增加人工数据生成和基准入口，复用确定性 factory、生产查询、真实 PG 与受控 provider；产物写 .scratch/。
- 登记 1 千、1 万、10 万封、多账号、多目录/位置、同排序时间、附件和不同正文长度数据集；日常可选轻量，定期执行大数据集。
- 记录首页/深分页/搜索/统计、同步/归档和附件读取的延迟分位数、吞吐、RSS、DB/Blob 空间、查询计划及环境元数据；建立人工可审阅基线，不预先承诺硬件无关 SLA。

### 非范围

- 不为达到尚未测量指标重构生产实现，不新增缓存/搜索服务，不要求所有 PR 跑十万封基准。
- 不把空 HTTP 请求、Mock 数据或仅进程启动时间称为邮箱性能基准。

- [x] AC-001：同一 seed 和数据规模可重复生成同样语义的数据集，并记录账号/邮件/位置/附件数量与正确性校验；运行只使用本轮独立数据库和产物目录。
- [x] AC-002：对首页、深 keyset 翻页、中文/ASCII 搜索、未读统计、同步/归档和附件读取执行预热后至少三次测量，报告 p50/p95、样本数和吞吐，分页全程无重复/漏项且计数与真实 SQL 一致。
- [x] AC-003：报告同步采集被测进程峰值 RSS、数据库与 Blob 空间、查询计划，以及 OS/CPU、PG/Python/Node/依赖版本、数据 seed、提交及配置；缺少必要度量时失败，不以空字段输出成功。
- [x] AC-004：本地轻量模式和定期十万封模式均有明确资源/超时上限、取消和清理路径；不会一次性将全部附件或邮件正文载入测试驱动内存来扭曲生产进程测量。
- [x] AC-005：同环境相同数据集两份报告能生成可读差异，包括延迟、RSS、空间及查询计划变化；不同环境明确提示不可直接比较，不凭未校准统一毫秒值宣告性能回归。

## 上下文区

- 来源：无外部条目；本会话测试评估、固定容器方案与用户批准（2026-10-22）。来源为本会话用户批准测试增强；性能结论尚未测量，task 交付为可重放基线与测量工具，不虚构当前性能或阈值。

### 有意不测

- 不做公网邮箱压测或承诺任意硬件十万封响应时延；不将基准结果当作生产负载容量保证。

### 测试策略

- 先验证数据和操作结果，再计时；区分准备、迁移、预热、测量和清理时间，避免把依赖下载算入请求耗时。
- 以生产 API/查询与同步路径驱动，数据生成成本单独报告；对坏数据、缺指标和超时做工具自身负向校验。
- 首份基线保留在可复现 CI 产物并在 testing.md 记命令/环境/结论，是否设回归预算依据实际波动另作明确决策。

### 风险与回退

- 风险：机器噪声、缓存状态、数据分布或监测工具本身影响结果；必须标记环境和预热阶段，跨机器不作直接通过/失败比较。
- 回退：回退本 task 单一执行 commit 恢复原入口与测试；仅回收本轮拥有测试资源，保留用户数据、其他 task 改动和失败证据。不更改生产 schema 或数据，迁移验证仅对一次性测试库操作。
