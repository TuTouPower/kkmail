# Task spec

## 背景

用户打开含外链图片的 HTML 邮件时，点击「仅此邮件允许加载」后图片仍停留在占位状态；刷新网页后放行状态完全丢失，再次出现拦截提示；也无法将某个发件人的邮件图片设置为长期允许。`p066` 已核实代码事实：放行状态仅存于 `MessageReader` 组件局部的单值 `useState`，既未持久化也未集合化；邮件正文 iframe 的 React key 不包含放行状态；后端当前没有任何远程图片放行记录。另有确定缺陷：归档层已把 `Content-ID` 存入附件表，但附件 DTO 不返回，前端也从不把 `cid:` 图片重写为可访问地址，导致内联图片在默认拦截与放行后都无法显示（`p067` 并入本 task）。同时，`p068` 记录的同类位点 `MessageReader.tsx:82`（`viewModeOverride` 单信深色覆盖）同样采用单值标量 `useState`，导致切换多封邮件时后操作的覆盖直接冲掉先前邮件的覆盖设置（`p068` 并入本 task）。用户已确认：单封邮件放行与发件人放行两类状态都必须入库持久化。无论浏览器是否会在 `srcdoc` 更新后重试图片请求，本 task 都在放行后强制重建正文文档；真实浏览器测试用于验收行为，不作为实施前提。

## 契约区

### 范围

- 服务端持久化两类远程图片放行：按邮件、按发件人地址。发件人白名单为服务端全局作用域（跨账号共享），以服务端解析出的结构化 `from_address` 为准；写入、命中与移除统一做去首尾空白加小写规范化后精确匹配，重复写入只保留一条记录。
- 邮件详情接口在附件列表（`AttachmentOut`）中返回 `content_id`；前端阅读器解析 HTML 正文，将 `<img src="cid:...">` 按 Content-ID 匹配对应附件，由父页面带认证获取附件数据以 `data:` URL 注入；未匹配保持原样。内联图片默认渲染，不受远程图片拦截规则限制。
- 维持沙箱安全基线不变：严禁为附件访问给 iframe 增加 `allow-same-origin`，亦不得依赖沙箱 iframe 发送会话 Cookie（已由 `docs/findings/d002_sandbox_iframe_omits_cookies_for_cid_attachments.md` 验证沙箱内不发同站 Cookie）。
- 放行请求必须由服务端确认持久化成功后才放开远程图片加载；失败时保持拦截、提示错误并允许重试。
- 邮件详情返回「当前邮件是否已放行」；阅读器以此决定是否加载远程图片与是否展示拦截提示。
- 拦截提示提供「仅此邮件允许加载」与「总是允许来自此发件人的图片」两个操作；后者仅在发件人地址可解析为有效邮箱时提供。
- 放行成功后，当前阅读器立即以全新邮件正文文档重新渲染并开始加载图片，无需用户手动刷新页面。
- 修复 `MessageReader` 单信深色视图覆盖（`viewModeOverride`）：从单值标量改造为按邮件 key 的字典/映射状态（`Record<string, 'smart' | 'original'>`），确保同一会话内为邮件 A 切换覆盖模式后，切换至邮件 B 操作不会抹除 A 的状态，切回 A 仍保持其覆盖视图。该覆盖仅在当前阅读器会话按邮件内存隔离，不入库持久化。
- 设置页提供已允许发件人的查看与移除；移除后当前会话重新打开相关邮件即恢复拦截，不依赖缓存自然过期。
- 数据库迁移、后端接口与前端 OpenAPI 契约同步更新。

### 非范围

- 单信深色视图覆盖（`viewModeOverride`）入库持久化（按前端会话独立保留即可，不增加数据库存储负担）。
- 域名级、图片托管域名级或全局「总是加载所有图片」白名单。
- 单封邮件放行的撤销界面；该记录仅在邮件删除时级联清理，发件人白名单可单独移除。
- 修改 DOMPurify 清洗规则、CSP 指令集合或 iframe `sandbox` 安全基线（不引入 `allow-scripts` 或 `allow-same-origin`）。
- 浏览器本地存储作为放行权威来源；本 task 明确改为服务端持久化。

### 验收标准

只写可观察、可独立验证的行为；每条使用稳定且不复用的 `AC-NNN`。需真实部署或人工环境验证时在编号前加 `[deploy]`。技术选型不作为行为 AC。

<!-- /规范 -->

- [ ] AC-001：默认情况下，含 http(s) 远程图片的 HTML 邮件不加载图片并显示拦截提示；不含远程图片的 HTML 邮件不显示提示；纯文本邮件不显示提示。
- [ ] AC-002：点击「仅此邮件允许加载」后，当前邮件无需手动刷新即开始加载远程图片，拦截提示消失。
- [ ] AC-003：单封邮件放行后，刷新网页、清空浏览器站点数据或在新的浏览器会话中重新打开该邮件，图片仍直接加载且不显示拦截提示。
- [ ] AC-004：单封邮件放行仅作用于该邮件；切换到其他未放行邮件仍拦截，切回已放行邮件仍直接加载。
- [ ] AC-005：点击「总是允许来自此发件人的图片」后，当前邮件立即加载；同一发件人地址（大小写与首尾空白归一化后相同）的其他邮件在刷新或新浏览器会话中不再显示拦截提示并直接加载图片。
- [ ] AC-006：发件人放行不影响其他发件人的邮件；发件人地址为空或不能解析为有效邮箱时，界面不提供该操作，服务端也拒绝保存该地址。
- [ ] AC-007：设置页展示已允许的发件人地址并支持移除；移除后，当前会话重新打开该发件人的已缓存邮件即恢复拦截，无需等待缓存过期；该邮件若另有单封放行记录则仍加载。
- [ ] AC-008：删除邮件后，其单封邮件放行记录随数据库级联清理且不残留；删除邮件不影响发件人放行记录。
- [ ] AC-009：放行状态变化不改变安全基线：未放行邮件的 CSP 图片源仍仅允许 `data:` 与 `cid:`，iframe `sandbox` 不含 `allow-scripts` 或 `allow-same-origin`，DOMPurify 过滤规则不变。
- [ ] AC-010：服务端对不存在的邮件返回未找到；重复放行同一邮件或同一发件人为幂等成功；Cookie 会话写请求沿用现有 CSRF 校验，合法 API Key 保持现有免 CSRF 行为。
- [ ] AC-011：邮件详情返回的放行标志与实际记录一致：单封邮件记录命中或发件人记录命中任一成立即为已放行，两者均不命中即为未放行。
- [ ] AC-012：发件人白名单跨全部收件账号生效：同一地址在任一账号的邮件中放行后，其他账号中来自该地址的邮件同样直接加载；大小写或首尾空白不同的同一地址被视为同一条记录，移除时同样命中且列表中不出现重复项。
- [ ] AC-013：放行请求在服务端确认保存前不发起远程图片请求；请求失败时保持拦截并显示错误提示，用户可重试；请求未完成时切换到其他邮件，不把放行状态带到其他邮件。
- [ ] AC-014：默认拦截远程图片时，含匹配 Content-ID 附件的内联图片（`<img src="cid:...">`）仍正常解码显示；若邮件仅含内联图片，不显示远程图片拦截提示；若同时含远程图片，拦截提示仅针对远程图片，内联图片不受影响。
- [ ] AC-015：HTML 中 `cid:` 值与附件 `Content-ID` 存在大小写差异、URL 编码差异（如 `%40` vs `@`）或包裹尖括号（`<...>`）差异时，仍能正确匹配并显示；无匹配附件或出现多附件冲突时不误指错误附件，保持安全降级原样。
- [ ] AC-016：内联图片重写只作用于 `img` 标签的 `cid:` 协议地址；不放宽 iframe `sandbox`，未放行邮件的 CSP 不放开远程 `http(s)` 源，不发起跨域外部网络请求；通过父页面认证获取附件转 `data:` URL 注入，不依赖沙箱 iframe 发送 Cookie。
- [ ] AC-017：在深色模式下，对邮件 A 切换单信原样/深色覆盖后，切换至邮件 B 并进行切换操作，再切换回邮件 A 时，邮件 A 仍保留先前的覆盖状态，不被邮件 B 的操作冲掉；未单独切换覆盖的邮件继续遵循全局深色偏好。

- 创建前审阅：Codex `gpt-6.1-sol` 结论 `CHANGES_REQUIRED`；已按 findings 补发件人作用域与规范化、失败分支、缓存撤销与真实浏览器验证，并将 `cid:` 与 `viewModeOverride` 全部收编闭环。

### 有意不测

- 第三方广告拦截插件对图片的拦截：不受应用控制，使用本地测试图片服务器验证应用自身行为。
- 缺少 Content-ID 且无法唯一对应附件的非标 cid 图片：保持原样，不做猜测性映射。
- 域名级与全局放行：未定义产品语义，本 task 不覆盖。

### 测试策略

- 后端 PostgreSQL 集成测试：两类放行记录的写入、幂等、大小写与空白规范化、跨账号全局命中、详情标志计算、非法发件人拒绝、邮件删除级联与发件人白名单独立保留；迁移升级与降级。
- 后端 API 契约测试：`AttachmentOut` 暴露 `content_id`；新放行接口状态码与 OpenAPI 生成一致性；无认证写请求拒绝，Cookie 会话缺失或错误 CSRF 拒绝，合法 API Key 保持免 CSRF。
- 前端组件测试：默认拦截；点击单封放行后正文节点重建且 CSP 放开；详情返回已放行时无提示条并直接放开；发件人放行与非法地址隐藏操作；纯文本与无远程图片邮件不出现提示；设置页列表与移除；移除后重新打开缓存邮件恢复拦截；放行请求失败或无响应时保持拦截且切换邮件不串状态；`cid:` 大小写/编码/尖括号匹配与 data URL 注入测试；`viewModeOverride` 多邮件独立保留与切换测试。
- Playwright E2E：用可控图片服务器统计请求并确认图片成功解码，验证点击前无请求、点击后发起请求且可见，刷新后不重复拦截；发件人白名单对同发件人第二封邮件生效；失败响应不产生图片请求；验证含 `cid:` 内联图邮件在未放行远程图片时即正常显示图片（`naturalWidth > 0`）。
- 真实浏览器验证：实施时用真实 Chromium 验证图片渲染与解码，确认单封放行、发件人放行及内联图片展示全部通过。

### 风险与回退

- 风险：大体积内联图片在转为 data URL 注入时可能引起正文 DOM 内存占用升高；实现侧应仅针对 `cid:` 引用的图片类型附件按需获取与注入，且严禁因此破坏沙箱基线引入 `allow-same-origin`。
- 风险：已有用户此前在浏览器会话内临时放行的邮件在本变更后需要重新放行一次；属于预期的语义升级。
- 风险：历史未存储 Content-ID 的老邮件无法按 ID 匹配；保持安全降级原样。
- 风险：发件人地址规范化（大小写、空白、损坏报头）与前端展示不一致，导致白名单看似不生效；以统一规范化函数与跨层测试收敛。
- 风险：撤销白名单后未使已缓存详情失效，staleTime 内继续放行；以当前会话重新打开缓存邮件的测试覆盖。
- 风险：放行 API 尚未确认持久化就乐观放开图片，失败后远程请求已泄露访问事实；以失败分支的请求计数测试覆盖。
- 回退：撤销发布后执行迁移降级删除两张新增表即可；`AttachmentOut` 字段向后兼容，不改动既有数据。

### 依赖与约束

- 需要新增 Alembic 迁移与重新生成 OpenAPI TypeScript 契约。
- 不引入新的第三方依赖；沿用现有认证、CSRF 与 PostgreSQL 事务设施。
- 放行记录属于隐私边界变更：只有用户显式操作且服务端持久化成功后才写入并放开图片，默认拦截行为与 CSP/sandbox 基线不得放宽。
- 内联图片注入严禁放宽沙箱基线（`d002`）。
