# Task spec

## 背景

p074 已确认：部署备份失败并非 blob 写入权限缺陷。blob 与应用数据按私有存储契约以应用 UID 创建，文件 `0600`、私有目录 `0700`；真正的问题在部署脚本为写入宿主 `0700` 备份目录，强制备份容器切到宿主 UID，导致同一进程既要读应用私有数据又要写宿主私有目录，跨了两个数据所有者。历史提交 `77622a45` 与 `4c00620f` 在两个方向来回调整，证明按现有边界无法稳定解决。

本 task 保留 blob 私有权限，重设计备份、宿主导出与恢复的身份和权限边界，并补齐真实身份/文件权限测试，避免继续用放宽权限或环境相关行为掩盖问题。

## 契约区

### 范围

- 统一应用数据所有者：API、Worker、备份与恢复进程使用明确且稳定的应用 UID；blob 文件 `0600`，私有目录 `0700`；备份容器对 blob 只读挂载。
- 备份在容器私有工作目录完成：由应用身份生成并校验密封包，不再直接写宿主 bind mount。
- 宿主侧导出与发布：部署脚本通过 Docker CLI/API 将完成的包导出到宿主所有的 `0700` staging 目录，再由宿主校验并原子发布为部署备份路径。
- 恢复遵循目标身份：以目标应用 UID 显式创建私有目录和文件，不继承归档 UID，也不依赖进程 umask。
- 存量权限归一化：提供受控维护路径，将现有 blob/备份目录统一到应用 UID + `0600`/`0700`，不在应用启动时递归修补。
- 调整部署脚本与 A13 测试：移除“备份容器必须使用宿主 UID”的实现锁定，改为验证真实身份能否读取应用数据、导出包归属与目录权限。
- 补充备份/恢复/部署边界的真实身份与文件权限集成测试及文档。

### 非范围

- 不修改 blob 加密算法、密钥轮换语义、备份包格式、`MANIFEST`/校验和契约。
- 不把长期命名 volume 作为强制架构；独立临时容器 + 宿主导出即可。
- 不在 API/Worker 启动时递归 `chmod`/`chown` 存量数据。
- 不改前端、邮件同步、账户与业务 API。
- 不在生产库上执行真实恢复；恢复验证只在隔离栈/演练环境进行。
- 不放宽 blob 目录或备份目录权限来适配部署。

## 上下文区

- 来源：p074（2026-11-05 核实）。当前代码仍为：blob 写入/轮换最终 `0600`（`src/mail_core/blobs/store.py:128`、`:190`、`src/mail_core/blobs/rotate.py:185-196`）；部署脚本强制备份容器使用宿主 UID（`scripts/deploy_mail_core.sh:73`、`:76`）；恢复用 `open("xb")` 且未显式设定最终权限（`src/mail_core/backup/package.py:1589`、`:1596`）；A13 测试锁定宿主 UID 文本（`tests/scripts/test_deploy_mail_core_r4adopt_p51.py:62`）。本次事故中现场把存量 blob 临时改为 `0644` 只是解除部署阻塞，不是目标契约。

### 有意不测

- Windows 下的 Docker 文件归属与 UID 映射：当前部署路径与项目平台约束不覆盖 Windows，且无法在现有环境可靠验证。
- 真实生产库恢复：会破坏生产数据，仅做隔离栈恢复演练与权限回归。
- 密钥轮换的加密正确性：已有独立测试覆盖，本 task 只验证轮换后文件 owner/mode 与备份可读性。

### 测试策略

- 单元测试：覆盖权限辅助函数、恢复落盘时的显式 owner/mode、umask 参数化、目录遍历拒绝与失败清理；不得通过匹配脚本文本来断言架构身份。
- 集成测试：在隔离 Docker 环境创建真实 `0600` blob 与新写入/轮换后的 blob，运行备份容器（应用 UID、blob 只读），校验密封包与 verify 结果；以无关 UID 尝试读取，断言失败。
- 恢复测试：隔离 PostgreSQL + blob 根目录，分别以 umask `022`、`077` 恢复同一归档，比较 owner/mode；恢复后执行应用读写与再次备份回归。
- 部署测试：将 A13 从“脚本文本匹配宿主 UID”改为验证备份身份能读应用数据、宿主导出目录 `0700`、导出包归执行者、校验后原子发布；补充失败路径断言（不发布半成品）。
- 黑盒验证：在隔离部署栈运行 `scripts/deploy_mail_core.sh --no-push`，检查备份导出、健康检查、新邮件写入与再次备份。

### 未知契约清单

<!-- 规范（门禁必留，不得删除） -->

未核实的外部契约标为 `UNVERIFIED-BLOCKING` 或 `UNVERIFIED-SPIKE`；核实后改写为结论和验证方式。无则写“无”。

<!-- /规范 -->

- Linux 主机上 `docker cp` 从容器导出到宿主的文件归属：`UNVERIFIED-SPIKE`。本机 OrbStack 已实测导出文件归执行部署的宿主用户（`501:20`），需在 Linux 主机或 CI 复核；若行为不同，导出后由宿主显式 `chown` 到执行者并验证。
- macOS OrbStack 与 Linux 对容器 UID、bind mount、私有目录的组合行为：`UNVERIFIED-SPIKE`，由集成测试在目标平台验证；不依赖隐含的同一 UID 映射。

### 风险与回退

- 风险：容器私有工作目录占用容器可写层，备份包较大时可能受 Docker 存储上限影响；导出路径或 `docker cp` 归属在 Linux 上不同于 OrbStack；恢复权限收紧可能影响存量 `0644` 文件的读取；部署脚本在备份/导出失败时中断。
- 回退：保留旧备份包与 rollback 镜像标签；备份、导出、校验任一失败时脚本在构建/迁移/重启前退出，不发布半成品；权限归一化只改 owner/mode、不改文件内容，可按维护流程回退；恢复演练在隔离环境完成后再操作生产。

### 依赖与约束

- 需要 Docker/Compose v2 与可用的回环 API 端口；部署验证以项目现有 `scripts/deploy_mail_core.sh` 为准。
- 备份与恢复进程必须使用镜像声明的应用 UID；不得依赖宿主 UID 或运行时 `umask`。
- 现有备份包格式与校验契约保持不变；部署备份目录必须始终为宿主用户所有的 `0700`。
- 安全约束：blob 为密文但不因此放宽权限；无关 UID 不可读、目录不可遍历。
