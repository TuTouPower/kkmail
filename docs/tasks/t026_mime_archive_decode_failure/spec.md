# Task spec

## 背景

t007 修复 IMAP 元数据报头解析，但 MIME 归档仍使用 email.policy.default 及原生 str/get_filename，裸 GBK 主题、发件人和附件名可在解析时损坏。p020 同时要求真实不可恢复数据显式失败，禁止运行时隐式修复历史脏数据。本 task 处理归档入口，保留原始字节直到解码，并区分可确定解码与真实损坏；不扩展为历史修复工程。

## 契约区

### 范围

- 修复归档 MIME 报头提取和附件文件名解码，覆盖 Content-Disposition filename 与 Content-Type name 回退路径。
- 对无法无损解码的目标报头/文件名或已确认导致解析无法完成的结构破损，记录明确、脱敏且可定位的失败，阻止损坏派生产物入库。
- 保留原始 MIME 可恢复性，覆盖归档状态、正文/附件派生结果、缺失元数据提取及搜索索引的一致性。回填与失败状态边界须先解决下方阻塞项。

### 非范围

- 不增加历史乱码扫描、读取时纠正、自动重归档或隐式自愈；不执行生产库数据修复。
- 不改变 IMAP 元数据扫描入口 t007 已有字段级降级契约，不把归档严格失败扩成所有同步报头全局失败。
- 不新增服务商、MIME 正文主题样式功能或通用数据清洗框架；不因合法缺失可选字段拒绝邮件。

### 验收标准

<!-- 规范（门禁必留，不得删除） -->

只写可观察、可独立验证的行为；每条使用稳定且不复用的 `AC-NNN`。需真实部署或人工环境验证时在编号前加 `[deploy]`。技术选型不作为行为 AC。

<!-- /规范 -->

- [ ] AC-001：从尚未具备元数据的原始 MIME 归档时，裸 UTF-8、GBK/GB2312、ASCII、有效 RFC 2047 及混合/折行报头被确定解码；主题、发件人姓名/地址与对应搜索文本一致，不因提前替换原始字节产生乱码。此条按保留缺失元数据提取方案拟定，须先确认阻塞项。
- [ ] AC-002：附件名来自 Content-Disposition filename 或 Content-Type name 时，裸 GBK、UTF-8、有效 RFC 2047、RFC 2231 扩展参数及连续参数可还原预期名称；标准声明有效时遵守声明，无有效声明时按严格 UTF-8、严格 GB18030 顺序尝试。合法缺名仍使用既有确定性默认名，路径清理、附件身份和内容保持正确。
- [ ] AC-003：目标报头/附件名字节无法按有效声明或确定回退无损解码，或 MIME 结构确实不可解析时，不以替换符结果、猜测名称或损坏元数据冒充解析成功；记录带 message_id 和错误类别的脱敏警告及持久 parse_error，保留原始 MIME。拟保留原文归档完成与解析失败并存的既有模型，不静默吞错；此状态语义须先确认阻塞项。
- [ ] AC-004：一封损坏邮件不阻断同批其他合法邮件归档；失败邮件不提交已判定损坏的正文、附件名、元数据或其搜索派生结果；错误记录与原文保留结果一致，不将解析失败误报为正常完整解析。
- [ ] AC-005：既有非空主题、发件人与历史乱码字段不因归档检测而被推测修复；正常读取不扫描或写回历史记录，既有有效邮件的正文、附件下载、稳定附件标识及原文访问保持可用。

## 上下文区

- 来源：p020（2026-10-23 核实；无等价 effective task）。.scratch/repro_header_mojibake_gap.py 对照生产回填 policy 复现主题乱码，而保留字节后使用现有解码逻辑得到完整中文；.scratch/repro_attachment_filename_gbk.py 直接调用生产 parse_mime_content，文件名“测试文档.pdf”变成含替换符字符串。archive.py 的报头回填异常只记 debug，外层 MIME 解析异常虽记 parse_error，后续仍可完成原文归档。test_blob_archive_fixes.py 已有 ASCII 缺失元数据回填测试，test_archive_mime_parser.py 主要覆盖 ASCII 文件名与存储失败，未覆盖这些编码及真实损坏分支。

### 有意不测

- 真实业务库历史乱码恢复：本 task 明确不执行历史修复；使用合成 MIME 和独立测试库，不读取用户邮件。
- 所有邮件格式缺陷穷举：只严格处理本次目标报头、附件名及已确认阻断解析的结构破损，合法可选字段缺失不等于格式损坏。

### 测试策略

- 先为当前生产 parse_mime_content、归档报头入库及搜索索引写失败回归，覆盖裸编码与标准声明、混合/折行、filename/name 两入口、RFC 2231 连续参数、缺名和原始字节已不可恢复情况。
- 使用真实 PostgreSQL 与加密 BlobStore，贯通 run_archive_batch，断言 Message、MessageBody.parse_error、Attachment、MessageSearch、原始 Blob 链接及状态一致；不能只测试孤立 decoder。
- 混合合法和损坏邮件批次验证隔离；区分解析失败与写盘/配额失败，核对失败记录脱敏、原文仍可恢复且无损坏派生产物提交。
- 保留旧语义仍有效的测试；若产品确认移除回填或改变解析失败状态，按 TDD 规范整体删除失效旧测试并说明理由，不就地将预期改成新输出。

### 未知契约清单

<!-- 规范（门禁必留，不得删除） -->

未核实的外部契约标为 `UNVERIFIED-BLOCKING` 或 `UNVERIFIED-SPIKE`；核实后改写为结论和验证方式。无则写“无”。

<!-- /规范 -->

- 缺失元数据提取保留范围：UNVERIFIED-BLOCKING。p020 禁止“历史数据隐式自愈”，尚未明确是否也移除现有归档缺失字段回填。已询问用户；当前推荐只保留初次归档缺失字段提取，不扫描或修复既有乱码。确认后固定 AC-001/AC-005 及旧回填测试处置，不得 start 前自行假定已获批准。
- 不可恢复解析失败后的原文归档状态：UNVERIFIED-BLOCKING。已询问用户是否沿用“原文可完成归档，同时 parse_error 明确失败”，还是要求整个归档失败。确认后固定 AC-003/AC-004 和状态测试；未确认前禁止 start。
- 外部格式无新未知契约；沿用现有 email 解析能力和已验证解码回退，运行时必须区分合法可选字段缺失与真实不可恢复损坏。

### 风险与回退

- 风险：过度严格会误拒合法非标准邮件；提前有损解码会丢失证据；解析中途修改 ORM 后捕获异常可能留下部分损坏派生记录。
- 回退：回退本 task 执行 commit；始终保留原始加密 MIME，不删除业务数据。历史数据修复须另行授权，并先验证备份可恢复和迁移可回退。

### 依赖与约束

- 无硬依赖；t007 已完成。涉及邮件编码协议及持久化一致性，review_level=full。
- 复用现有解码能力和 MIME 参数解析，保留原始字节；如抽取共享 helper，仅服务本次两个生产入口，不构建推测性框架。
- 归档严格失败不改变 conventions.md 现有 IMAP 扫描损坏字段独立降级规则；若需要更新文档，明确入口作用域。
- 两项产品阻塞确认后才能 start；本次仅登记 backlog。

- `docs/blueprint/decisions.md`：运行时不隐式修复历史脏数据；明确缺失元数据提取与原文归档/解析失败的最终边界。
