# Intensive Review — 视角2 正确性与并发竞态 (Correctness & Concurrency)

## 视角摘要

并发与异步、生命周期控制、空值与状态机、资源释放、时序与协议异常。

## Findings

- [Critical][98] src/desktop/main.js:189 — 桌面端缺失单实例锁导致多进程写同一数据库与共享服务被误杀 — `main.js` 未调用 `app.requestSingleInstanceLock()`。用户二次启动 kkmail 时，实例2检测到 `pgData` 处于运行态且端口被占，随即绑定临时端口并拉起第二个 sidecar，两者并发读写同一 `userData` 数据库与 blobs 目录造成数据损坏；实例2关闭时触发 `shutdownAll()` -> `pg.stop()`，直接通过 `pg_ctl stop -m fast` 杀掉共享 PostgreSQL 集群，导致实例1崩溃 — 在入口处增加 `app.requestSingleInstanceLock()`，若未获取则退出并聚焦已有窗口。
- [Critical][95] src/mail_core/realtime/dispatcher.py:144-150 — 多 API 进程部署下无本地订阅者误标 dispatched 导致跨进程实时通知静默丢失 — `_fanout()` 中若当前进程无匹配目标（`targets` 为空），直接 `return True`，随后将该事件加入已分发列表并调用 `mark_dispatched()`。当多进程部署且各客户端连在不同 Worker 进程时，进程 A 抢先消费未属于自己客户端的事件并将其从数据库置为已分发，导致连接在进程 B 上的真实订阅客户端永远无法收到推送 — 仅当存在本地订阅且投递成功或采用分布式分发模型时才推进全局位点。
- [High][95] src/frontend/src/components/MessageReader.tsx:22 — loadRemoteImages 状态重置滞后导致邮件切换时瞬间泄露远程图片请求 — `loadRemoteImages` 通过 `useEffect(() => { setLoadRemoteImages(false) }, [selectedKey])` 重置。在 React 渲染管线中，`selectedKey` 变化时组件首先以旧状态（`loadRemoteImages=true`）执行初次渲染，构建带有 `img-src https: http:` 的 `srcdoc` 并赋给 iframe，浏览器内核立即发起新邮件正文中的远程图片请求，随后 effect 才执行将其置为 false，导致防追踪设计在切换邮件时完全失效 — 改用消息 ID 集合派生是否允许远程图片，或为 iframe 挂载动态 key 保证 DOM 同步销毁重建。
- [High][92] src/desktop/main.js:231 — 关闭流程中 PostgreSQL 先于 sidecar 停止导致后端事务与连接异常中断 — `shutdownAll()` 中 `stopBackend()` 仅发送异步 `SIGTERM`，紧接着下一行立即同步调用 `pg.stop()` 执行 `pg_ctl stop -m fast -w`。PostgreSQL 瞬间断开并终止连接，此时正在执行退出收尾、事务提交和状态落盘的 `mail-core` 后端连接被强制切断，导致后端抛错崩溃并可能遗留脏状态 — 编排受控退出时序：等待 sidecar 完全退出后再停止数据库服务。
- [High][92] src/frontend/src/components/MessageReader.tsx:202 — 附件下载链接触发 Electron 主窗口顶层导航导致 SPA 白屏被替换 — 附件链接 `<a href={mailCoreAttachmentUrl(att.id)}>` 未配置 `download` 属性与 `target="_blank"`。在 `main.js:166` 的 `will-navigate` 监听中，附件 URL 属于同源应用链接（`isLocalAppUrl` 返回 true），Electron 允许顶层导航。当用户点击 PDF、图片等浏览器内置支持预览的附件时，主窗口直接导航至附件流，整套 React SPA 被顶层替换无法返回 — 为附件链接显式添加 `download` 属性，并在 Electron `will-navigate` 中拦截附件路径改由外部/下载流处理。
- [High][90] src/mail_core/api/sse.py:157-198 — SSE 连接计数器提前递增且释放滞后于生成器导致连接槽位伪耗尽报 503 — 接口在第 157 行调用 `_acquire_sse_slot()` 递增全局激活计数器，而释放操作却位于异步生成器 `gen()` 的 `finally` 块中（第 198 行）。若客户端在建立 TCP 后立即主动断开，或中间件在生成 `StreamingResponse` 之前抛出异常，`gen()` 根本不会启动迭代，导致 `_sse_active` 计数器只增不减，迅速达到 `MAX_SSE_CONNECTIONS`（默认 128）并持续报 503 拒绝所有合法请求 — 将获取操作移入生成器内部最前端或使用可靠的异步上下文管理器绑定生命周期。
- [High][85] src/mail_core/sync/leases.py:121-129 — assert_fencing 忽略租约过期与主动释放状态失去互斥保护 — `assert_fencing()` 仅检查 `fencing_token` 是否相等，完全未检查 `row.lease_expires_at > now`；同时 `release_lease()` 释放租约时仅将过期时间置为 now，未推进 fencing token。若 Worker 因长 GC 或慢 I/O 导致租约过期，只要期间无其他 Worker 抢占推进 token，该 Worker 醒来后仍能通过校验并提交数据，时效互斥失效 — 在 `assert_fencing` 中增加过期时间判定，并在释放时推进 token。
- [High][85] src/mail_core/providers/imap.py:255-258 — IMAP UID FETCH 单封邮件空响应抛出异常导致文件夹同步死循环 — 在 `fetch_metadata_page` 循环中，若 SEARCH 获得 UID 后邮件在服务端被其他客户端删除，IMAP 返回 `typ="OK"` 且 `fetched=[None]`。此处直接抛出 `RuntimeError`，导致 Worker 捕获异常后任务失败回滚；由于当前页 cursor 未推进，下次重试仍拉取相同 UID 并再次报错，直至达到最大重试次数导致同步任务永久 FAILED — 空响应应判定为邮件在远端已删除，跳过该 UID 继续同步，不抛出致命异常。
- [Medium][90] src/frontend/src/components/MessageList.tsx:158 — 分页游标重叠未去重导致 React 重复 key 警告与状态错乱 — `raw = pages.flatMap((p) => p.items)` 未按 `m.id` 去重。在后台轮询同步或邮件插入导致游标位移时，跨页拉取易返回同一封邮件。`visible.map` 中以 `mailKey(m)` 为 key，触发 React `Encountered two children with the same key` 警告，导致虚拟 DOM 节点复用异常与选择框状态错乱 — 在 `raw` 组装时使用 Map 或 Set 按 `m.id` 进行去重。
- [Medium][85] src/mail_core/mail/storage/folder_stats.py:15-39 — recompute_folder_stats 缺乏行级锁导致并发未读数更新覆盖与初次插入竞争 — 先执行无锁聚合再 `session.get(FolderStats, folder_id)` 未使用 `with_for_update=True`。前端标记已读与 Worker 同步新邮件并发执行时，后提交者会无条件覆盖先提交者的统计结果（Lost Update）；初次插入时并发 savepoint 捕获 `IntegrityError` 易引发锁等待冲突 — 在聚合前锁定行，或使用 PostgreSQL 原生 `INSERT ... ON CONFLICT DO UPDATE`。
- [Medium][80] src/mail_core/threading/rules.py:176-184 — 消息线索关联并发创建新 Thread 缺少冲突保护导致同步中断 — `threads` 表在 `(account_id, provider_thread_key)` 上有唯一约束。当同一会话的多封邮件同时到达并由并发工作流处理时，均发现 thread 为 None 并尝试插入，后执行者抛出 `IntegrityError` 导致整个元数据批次同步失败 — 创建 Thread 时使用 savepoint 捕获 `IntegrityError` 并重新加载已存在的记录。
- [Low][88] src/desktop/main.js:166 — 桌面端未监听 will-redirect 导致 HTTP 重定向未受拦截保护 — `webContents` 仅拦截了 `will-navigate`，未监听 `will-redirect` 事件。若被访问服务返回 HTTP 302/307 重定向至外部不受信地址，导航无法被就地阻断 — 增加 `will-redirect` 监听实施同等外链校验与系统浏览器分流。
