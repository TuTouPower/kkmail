# Task spec

## 背景

用户说明历史乱码已经手动处理，当前无需历史乱码修复；明确要求今后任何邮件解析错误直接在前端报错。当前归档虽会持久记录部分 parse_error，报头提取异常却只记 debug，正文异常还有静默回退；详情 API 已返回 parse_error，但 mailCoreToMailDetail 丢弃该字段，MessageReader 未显示，解析失败可能被误报为“尚未完成同步或内容为空”。本 task 交付 MIME 解析失败从后端持久记录到阅读器报错的完整链路。

## 契约区

### 范围

- 覆盖归档 MIME 正文、报头及附件文件名解析：已发生异常、解析器报告的失败以及可确定的有损解码失败，统一保留错误并向前端传递，禁止吞错后伪装成功。
- 复用 MessageBody.parse_error 与现有详情 API，贯通前端类型、数据转换和 MessageReader，打开失败邮件时明确显示解析失败。
- 保留已保存原始 MIME，区分原文保存成功与内容解析失败；正常邮件、合法空正文与尚未完成归档保持原有行为。

### 非范围

- 不核查或修复历史乱码，不扫描已有字段，不做读取期自愈、自动重归档或业务库数据操作。
- 不新增裸 GBK 等历史乱码专项兼容、推测性编码兜底或通用数据清洗框架；现有正常解析与合法缺失字段提取保持原语义。
- 不扩展至全局 IMAP 元数据扫描、网络错误或所有应用错误处理，不改 t007 扫描字段级降级契约。
- 不新增全局通知系统、弹窗风暴或归档状态机重构；报错位于对应邮件阅读界面。

- [ ] AC-003：归档 MIME 正文、报头或附件文件名发生解析异常、解析器报告失败或可确定的有损解码失败时，持久记录该邮件 parse_error 并输出脱敏日志；不得仅记 debug、转为空内容或静默降级后丢失错误。日志和错误可定位邮件及失败阶段，不泄漏凭据、完整原文或内部堆栈。
- [ ] AC-004：一封邮件解析失败不阻断同批其他合法邮件归档；已保存原始 MIME 保留可恢复性，不提交已确认损坏的派生结果，也不将该邮件冒充完整解析成功。沿用原文归档与解析结果分离模型，无需因解析失败反复下载同一原文。
- [ ] AC-005：读取邮件不扫描、覆盖或推测修复历史字段；正常邮件正文、附件和现有合法缺失字段提取行为保持可用。用户已手工处理的数据不因本 task 自动触发重解析或改写。
- [ ] AC-006：详情 API 返回 parse_error 后，前端类型与转换完整保留该状态；阅读器在该邮件中显示清晰、可访问的“邮件解析失败”提示及脱敏原因，即使接口 HTTP 成功、存在摘要或部分内容也必须提示，不显示“尚未完成同步或内容为空”来掩盖失败。
- [ ] AC-007：从失败邮件切换至正常邮件后，旧错误不残留；重新打开失败邮件或刷新后仍能看到持久失败。没有 parse_error 的合法空正文或待归档邮件仍显示相应原提示，不被误判为解析失败。

## 上下文区

- 来源：p020；2026-10-23 用户澄清“目前这些乱码的应该都已经手动修复了……有任何解析出错的地方，就直接在前端报错”。历史修复由用户说明，本次未连接业务库复核。
- 当前核实：archive.py 仅部分外层解析异常写 MessageBody.parse_error，报头提取异常只记 debug，parse_mime_content 正文 get_content 异常有静默回退；queries.py/get_message_detail 和 MessageDetailOut 已返回 parse_error，生成 API 类型已有字段；mailCoreToMailDetail 未透传，MessageReader 未消费。
- 原 AC-001、AC-002 编码修复专项随本次范围澄清撤销，编号永久保留，不复用；AC-003 至 AC-005 按既有错误记录、隔离及历史数据保护行为收敛，新增 AC-006/AC-007 覆盖前端报错与状态隔离。旧产品问题已由当前范围及沿用现有存储模型消除。

### 有意不测

- 历史业务库乱码是否全部修复：用户已说明处理情况，本 task 不访问或迁移生产数据。
- 新增各种编码兼容与乱码恢复算法：已移出范围；可用合成非法字节触发错误报告，但不要求猜测还原文本。
- 全应用解析器与外部服务错误穷举：本 task 限定邮件 MIME 归档正文、报头、附件名链路。

### 测试策略

- TDD 先补回归：MessageDetailOut 带 parse_error 且 HTTP 200，生产转换与阅读器仍应保留并显示错误；覆盖无正文、有摘要、有部分正文和失败/正常邮件切换，防止只测 HTTP 拒绝或绕开转换直接塞组件数据。
- 正文、报头、附件名三个生产解析入口分别构造异常或解析器报告失败，触达真实 run_archive_batch，使用独立 PostgreSQL/BlobStore 验证持久 parse_error、API 返回、日志脱敏、原文保留及同批合法邮件完成；不能只 mock 一个孤立 helper 就声称全链路通过。
- 覆盖合法空正文、待归档、正常正文与附件；不因缺失可选字段或文本本身合法含替换字符而误报，不用“发现 U+FFFD 就认定历史乱码”替代解析失败证据。
- 浏览器端到端测试经生产数据转换验证错误可见、刷新仍存在和跨邮件隔离；运行受影响后端、前端、类型及 UI 冒烟检查。若 API 契约确需变更，改源后重新生成 OpenAPI 与客户端并核对一致性。
- 旧语义有效测试保留；确需删除失效旧测试时说明理由，不就地将旧预期改成当前输出。

### 风险与回退

- 风险：异常被内部降级或宽泛 catch 吞掉；前端转换丢字段或摘要回退掩盖失败；只看字符猜测乱码会误报；错误原文可能暴露隐私。
- 回退：回退本 task 执行 commit；不删除原始 MIME 或历史数据，无历史修复与数据迁移。若实施发现必须改 schema，应先补可回退迁移及验证。

### 依赖与约束

- 无硬依赖；t007 已完成。涉及解析失败与持久化一致性，保留 review_level=full。
- 优先复用既有 parse_error、详情 API、错误脱敏与前端语义 token；不为单个错误链路建设全局事件系统。
- 当前任务涉及 MessageReader 与 mailCoreToMailDetail；与 t024 侧栏、t025 桌面复制核心代码独立。共享 blueprint 在集成时核对，真实窗口焦点测试错峰执行。
