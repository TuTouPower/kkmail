# Intensive Review — 视角4 性能与资源消耗 (Performance & Resources)

## 视角摘要

数据库查询与索引、算法复杂度与重复计算、IO 与网络往返、缓存机制、前端渲染与主线程阻塞。

## Findings

- [Critical][95] src/mail_core/security/auth.py:206-288 — 会话认证每次 HTTP 请求无缓存直接建立 DB Session 查库消耗连接池 — 每个带有 Cookie 的请求进入 `require_auth` 时均调用 `read_session()`，其第 281 行调用 `get_session_epoch()`。`get_session_epoch()` 内部无内存缓存且不复用外层 session，每次均打开独立 session 查询 `AuthCredential`。所有常规读取与轮询请求在执行业务逻辑前，都先向连接池借用连接发一次同步 SQL。高频并发时瞬间耗尽连接池（默认 `pool_size=10`），导致正常业务接口报连接池等待超时 — 在内存全局变量中缓存 `_session_epoch` 并设定短期 TTL 或在修改密码/强制注销时主动使缓存失效，禁止在认证路径上每次请求开启独立 DB 事务。
- [Critical][90] src/mail_core/blobs/archive.py:158-216 — 核心状态表 message_archive_state 缺少二级索引导致 Worker 高频全表扫描 — 在 Alembic 迁移中，`message_archive_state` 表仅建立了 `message_id` 主键，未建立任何二级索引。Worker 调度器高频轮询 `claim_archive_batch`（按 state、claimed_by、priority 过滤）、`reclaim_stale_archive_claims` 以及 `resume_quota_paused_archives`。随着邮件累积，每次轮询均对该表执行全表扫描，严重耗尽磁盘 I/O — 添加复合条件索引：`CREATE INDEX ix_archive_claim ON message_archive_state (state, priority) WHERE claimed_by IS NULL;`。
- [High][95] src/frontend/src/App.tsx:108 — ColumnResize 拖拽触发全局组件树无节流全量重渲染与高频同步写 localStorage — `ColumnResize` 的 `onDrag` 在每次 `pointermove`（60~120Hz）触发 `setSidebarWidth` / `setListWidth`。`App.tsx` 订阅了该宽度导致整个应用全量重渲染；子组件 `Sidebar`、`MessageList`、`MessageReader` 均未包裹 `React.memo`，每次鼠标移动均导致整个邮件列表 DOM 与正文 DOM 深度重渲染；同时 `mailStore.ts` 使用 persist 中间件，每次拖拽像素级高频同步执行 `localStorage.setItem` 阻塞主线程 — 拖拽期间仅通过原生 DOM style 或 CSS 变量更新宽度（结合 requestAnimationFrame），释放鼠标时才将最终宽度提交至 store 并持久化；为三大主要组件添加 `React.memo`。
- [High][95] src/frontend/src/components/MessageList.tsx:182 — 邮件列表过滤与排序未 memoize 导致每次渲染触发数千次正则解析 — `visible = raw.filter(...).sort((a, b) => compareMailDates(a.date, b.date, sortNewest))` 未包裹 `useMemo`，任何无关渲染（如选中切换、多选勾选）均全量重算。`compareMailDates` 内部每次比较均通过正则解析 IMAP/ISO 日期格式；对 300 封邮件排序执行数千次正则解析，显著消耗主线程 CPU — 使用 `useMemo` 缓存排序结果，并在数据接入层预先解析并缓存毫秒时间戳 `dateMs`。
- [High][90] src/mail_core/threading/rules.py:149-168 — messages.internet_message_id 缺失索引导致线程推导全表扫描 — `messages` 表在 `internet_message_id` 列上无索引。在 `assign_thread_for_message` 中，对新邮件提取的每个 `In-Reply-To` 和 `References` 标识符均执行 `where(Message.account_id == account_id, Message.internet_message_id == mid)` 查询。在同步含有长引用链的邮件批次时，针对每封邮件的每个 reference 均对 `messages` 表执行顺序扫描，导致元数据同步时间急剧恶化 — 添加索引：`CREATE INDEX ix_messages_account_internet_id ON messages (account_id, internet_message_id);`。
- [High][90] src/mail_core/providers/imap.py:249-388 — IMAP 抓取元数据与 Flags 循环逐条 FETCH 引发大量网络往返 RTT — `fetch_metadata_page` 与 `_fetch_flags_for_uids` 未利用 IMAP 协议标准的 UID 序列集语法（如 `1,2,3,...`），而是在 Python 循环内串行发送数十到数百次单个网络请求。若网络 RTT 为 50ms，单次同步等待网络耗时高达数秒至数十秒 — 合并 UID 列表为逗号分隔的序列集，单次 FETCH 完成全量元数据或 Flag 批量拉取。
- [High][85] src/mail_core/search/index.py:40-89 — 全文搜索 from_text 缺少三元组索引导致 GIN 索引失效退化为全表扫描 — `_MATCH` SQL 模板中同时匹配全文检索及模糊查询（`from_text ILIKE '%' || :q || '%' OR from_text % :q`）。迁移 `20261021_0006` 仅为 `subject` 创建了三元组索引。由于 `from_text` 上没有三元组索引，PostgreSQL 评估包含 `from_text` 的 OR 表达式时无法走 Bitmap Index Scan，被迫对 `message_search` 执行全表顺序扫描 — 添加迁移：`CREATE INDEX ix_message_search_from_text_trgm ON message_search USING GIN (from_text gin_trgm_ops);`。
- [Medium][98] src/frontend/src/components/Sidebar.tsx:19 — 轮询不存在的 API 产生确定性 404 网络开销与兜底放大 — `fetchAccountFolders` 优先请求 `/api/accounts/${encodeURIComponent(accountId)}/folders`，该接口在后端路由中根本不存在（仅存在 `/api/mail/accounts/{id}/folder-stats`）。每次账户列表刷新均产生必然失败的 404 HTTP 请求，随后才异常降级，成倍放大网络负载与控制台报错 — 移除失效路由调用，统一直接请求 `/api/mail/accounts/{id}/folder-stats`。
- [Medium][92] src/frontend/src/components/MessageReader.tsx:190 — DOMPurify.sanitize 在组件渲染主链路无缓存同步重跑 — `MessageReader` 每次重新渲染均在 JSX 展开阶段无条件调用 `buildMailSrcdoc(body, { loadRemoteImages })`，导致大邮件 HTML 被 DOMParser 反复解析、过滤和序列化，阻塞渲染 — 将生成的 srcDoc 结果用 `useMemo` 进行缓存。
- [Medium][90] src/desktop/logRotation.js:87 — RotatingLogStream 同步写盘阻塞 Electron 主进程事件循环 — `write` 方法中直接调用 `fs.writeSync(this.fd, buf)`。`mail-core` sidecar 同步日志高频输出时，主线程被连续同步 I/O 阻塞，直接导致桌面端窗口卡顿、掉帧 — 改用异步文件流 `fs.createWriteStream` 或内存缓冲批量异步刷盘。
- [Medium][85] src/mail_core/blobs/gc.py:52-162 — Blob GC 全表扫描所有记录及循环单条探测清理 — `mark_unreferenced_blobs` 无条件加载全部 `MessageBlob` 对象到内存，`sweep_expired_blobs` 全表扫描且无 limit；在 `unlink_gc_paths` 阶段逐个执行单条探测 SQL。当存储大量 blob 时易引发 OOM 与海量小查询 — 采用 Keyset 分页扫描，并添加 `(ref_count, gc_eligible_at)` 索引与批量预查。
- [Medium][85] src/mail_core/worker/main.py:68-85 — Worker 主轮询每次循环均无节制执行全表清理导致高频 DB 压力 — 主循环 `_tick()` 默认每 2 秒同步调用一次 `_reclaim_once()`，串行执行 4 项跨表清理与修剪任务，导致空闲状态下数据库 CPU 和 I/O 长期居高不下 — 将清理修剪任务移出高频循环，由独立的定时器按 1~5 分钟间隔执行。
- [Medium][85] src/mail_core/sync/reconcile.py:84-114 — Reconcile 与 Delta 删除循环内执行 3 次单个查询与 Flush (N+1) — 在处理待删除邮件循环中，针对每封邮件逐一执行 3 次独立 SQL 查询与 1 次 flush。在大量清理场景下产生数千次往返并显著拉长事务时间 — 利用 `in_()` 批量检索与批量删除。
- [Medium][80] src/mail_core/mail/application/mutations.py:151 — set_message_flagged 冗余重算全部未读数与聚合计数 — 标记邮件星标状态仅变更 `is_flagged`，不影响文件夹的 `total_count` 和 `unread_count`，代码无条件调用 `_recompute_stats_for_folders` 引发无意义的全量聚合扫描 — 移除星标操作中对 `_recompute_stats_for_folders` 的冗余调用。
- [Low][75] src/mail_core/api/accounts.py:170 — 账号管理接口为单个账号全量聚合统计所有 Groups — 返回单个 `AccountOut` 时无条件调用 `list_groups(session)` 查出所有分组并进行 group by 计数 — 仅当 `acc.group_id` 存在时按 ID 单条查询。
