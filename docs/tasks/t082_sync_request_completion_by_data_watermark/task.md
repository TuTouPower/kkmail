# Task spec

## 背景

p083（2026-11-22 用户实报 + 两张截图）：账号 `fengandelliot@gmail.com` 在 Gmail 有 2,403 封邮件，点「立即同步」后界面红字「立即同步失败：The bound sync execution no longer exists」，同时显示「收件箱已同步，后台正在同步其余文件夹...」。核查生产库与日志：邮件实际已入库（11,182 条，最新三封时间与截图 12:37 CST 吻合），账号 credential/connectivity 正常；失败源于主请求的 inbox target 绑定在一个从未 materialize 的预分配后继执行代际上，巡检把它判成 `execution_lost`。

根因是抽象错位：用户请求以「观察某一次具体任务执行」判定完成，而任务执行天生易变（重试、回收、合并、清理）。此前多次修复（决策时重检、锁顺序统一、代际提取优化）都在同一错误抽象上打补丁，只覆盖已知竞态窗口。按开发铁律，必须从根因重构：请求完成改由数据本身判定，彻底删除「观察执行代际」这层抽象，execution_lost 状态类随之消失。

## 契约区

### 范围

- 重构同步请求完成判定：由「绑定并观察具体执行代际」改为「数据水位」语义——请求记录发起时的数据目标，某次同步遍历覆盖该目标后请求即完成；完成不再取决于某一次任务执行的存活状态。
- 删除承载「请求观察某次执行」的数据结构与预分配后继代际机制（绑定表、代际预留与后继 materialize、孤儿绑定巡检的 execution_lost 分支），配套数据库迁移清理历史数据。
- 同步任务改为幂等：任何时刻对同一范围重新触发同步都安全；任务重试、认领超时回收、同键合并、历史任务清理都不影响请求收敛。
- 重建失败语义：只有数据确实无法推进（凭据失效、权限拒绝等明确原因）才判请求 failed 并给出用户可理解文案；瞬时错误交给重试。请求需有界终止，无任务推进时给出可操作提示。
- 前端移除内部实现术语的透传：错误横条不得原样显示「The bound sync execution no longer exists」类文案。
- 保留 A21 解耦语义：收件箱数据就绪后主请求完成，其余文件夹继续后台同步，后台结果不污染主请求终态。
- 更新 spec `docs/specs/mail_sync_and_storage.md` 与 `inbox_ui_and_search.md` 的相关契约；p083 以 `transferred` 转办本 task（fix_ref=t082），本 task 完成后不再二次闭环。

### 非范围

- 不改同步引擎的协议适配（IMAP/Graph 连接、fencing、租约、限流退避、分页）与正文归档链路。
- 不改「立即同步」四处按钮的视图范围解析、等待至终态语义、旋转图标与批量逐户报错行为。
- 不做生产部署、不 push、不改现役 `.env` 与容器。
- 不保留旧失败状态或绑定结构的兼容层。

- [ ] AC-001：对已有大量邮件的账号点「立即同步」，当该范围数据已入库时，请求终态为 complete，界面不出现失败横条，且不出现任何内部实现术语（执行、代际、绑定、execution_lost 等）。
- [ ] AC-002：同步请求完成判定与单次任务执行生命周期解耦：任务重试、认领超时回收、同键合并或历史任务清理后，对同一范围再次同步，请求仍据数据状态收敛为正确终态；系统任何路径都不再产生 `execution_lost` 类失败。
- [ ] AC-003：同一范围并发或重复触发多次同步，所有请求收敛为 complete，入库数据不重复；请求之间不存在共同观察某次具体执行的耦合。
- [ ] AC-004：仅当数据确实无法推进（凭据失效、权限拒绝等明确原因）请求才判 failed，且 safe_message 为用户可理解的原因；瞬时网络错误经重试后数据推进的，请求最终 complete。
- [ ] AC-005：请求在无任务推进数据时有界终止，失败文案为用户可操作的提示而非内部术语，不出现永久 queued/running 的悬挂请求。
- [ ] AC-006：A21 解耦语义保留：收件箱数据就绪后主请求完成，其余文件夹后台继续；后台同步失败不改变主请求终态，也不把内部术语显示给用户。
- [ ] AC-007：请求报告的 `errors[].code` 不再出现 `execution_lost`；任何终态失败都带非空且用户可理解的 safe_message。数据库迁移执行后，承载旧观察关系的数据被清理，报告与列表行为一致。
- [ ] AC-008：`docs/blueprint/testing.md` 的 `test_cmd` 与 `blackbox_verify` 全量通过；无弱化断言、无临时补丁残留。

### 有意不测

- 真实 Gmail 账号在 2,403 封规模下的端到端人工点击：无稳定外网与真实凭据；以本地 provider 构造大目录与真实 PostgreSQL 集成测试覆盖根因，生产现象作为背景证据。
- 任意邮件服务商的协议细节差异：本 task 只改请求完成判定与失败语义，协议适配不在范围内。

### 测试策略

- 后端集成（PostgreSQL）：驱动真实请求创建、任务认领/完成/重试/回收/合并与报告端点，断言各场景下请求收敛到正确终态、无 execution_lost、失败文案可读；迁移后断言旧观察数据清理。
- 前端组件/E2E：断言「立即同步」成功无失败横条、失败只显示可理解文案，A21 后台与主请求状态不串扰。
- 门禁：`test_cmd` 与 `blackbox_verify` 全量通过。

### 风险与回退

- 风险：并发触发下同一范围多次遍历可能放大 Provider 请求；数据水位判定边界（请求发起与遍历启动的时序）处理不当会让请求悬挂或过早完成；迁移清理历史数据影响未结算的旧请求。
- 回退：按 AC 逐条关闭新语义并回退到旧完成路径；迁移以可重复执行方式编写，失败可回滚到迁移前版本；不靠缩短超时掩盖悬挂。

### 依赖与约束

- 依赖：A21 后台解耦语义与四处「立即同步」按钮契约保持不变；Worker 的去重键、租约与 fencing 语义不变。
- 约束：并发与迁移按 `full` review level 执行；不引入旧结构的兼容层。
