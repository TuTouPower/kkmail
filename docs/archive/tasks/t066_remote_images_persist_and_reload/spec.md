# Task spec

## 背景

用户打开含外链图片的 HTML 邮件时，点击「仅此邮件允许加载」后图片仍停留在占位状态；刷新网页后放行状态完全丢失，再次出现拦截提示；也无法将某个发件人的邮件图片设置为长期允许。`p066` 已核实代码事实：放行状态仅存于 `MessageReader` 组件局部的单值 `useState`，既未持久化也未集合化；邮件正文 iframe 的 React key 不包含放行状态；后端当前没有任何远程图片放行记录。另有确定缺陷：归档层已把 `Content-ID` 存入附件表，但附件 DTO 不返回，前端也从不把 `cid:` 图片重写为可访问地址，导致内联图片在默认拦截与放行后都无法显示（`p067` 并入本 task 闭环）。同时，`p068` 记录的同类位点 `MessageReader.tsx:82`（`viewModeOverride` 单信深色覆盖）同样采用单值标量 `useState`，导致切换多封邮件或进入设置页往返时覆盖设置丢失（`p068` 并入本 task 闭环，原历史 pending 中的范围排他描述在此统一更正）。用户已确认：单封邮件放行与发件人放行两类状态都必须入库持久化。无论浏览器是否会在 `srcdoc` 更新后重试图片请求，本 task 都在放行后强制重建正文文档；真实浏览器测试用于验收行为，不作为实施前提。

针对 `p067` 内联图渲染，经调研业界开源邮件客户端（Thunderbird 原生协议、Mailspring 桌面私有协议、SnappyMail 预签名链接、Zero Data URL 等）并完成架构评估，本 task 正式采纳 **方案 B（短期无状态 HMAC 签名 Token 链接 / Signed URL）**：保持 `iframe sandbox` 不变，由后端为正文内联图片附件签发限时只读预览 Token，前端将 `cid:` 重写为带 Token 的预览 URL，浏览器在沙箱内原生流式加载图片。该方案彻底避免了前端 Base64 内存膨胀，无需在前端维护严苛的大小配额防御，同时无缝兼容 Web SPA 与 Electron 桌面端。

## 契约区

### 范围

- 附件分类与下载边界定义（消除歧义，严格区分两类附件）：
    - **普通文件附件（`is_inline=false`）**：绝不自动下载。保持现有交互与架构不变，仅在用户于附件列表中显式点击时才触发下载或保存，不发起任何自动静默拉取，不签发免 Cookie 签名预览链接；
    - **正文内联图片附件（`is_inline=true` 且被正文 `<img src="cid:...">` 引用）**：属于邮件正文视觉排版不可分割的组成部分，由服务端为每个内联图片附件签发短期只读预览 Signed URL，前端阅读器渲染正文时将 `cid:` 节点替换为此 URL，浏览器在沙箱 iframe 内直接流式拉取并解码渲染；
    - **超限与降级边界**：异常、损坏或非受控格式的内联文件，仅降级为正文对应位置不自动渲染图片（正文保留占位），该文件在附件列表中仍完整保留，用户需要时仍可在附件列表手动点击下载。
- 服务端持久化两类远程图片放行：按邮件（主键/外键关联 `mail_id`）、按发件人地址（服务端全局跨账号共享）。
- 发件人白名单服务端唯一权威与规范化：以服务端存储的结构化 `from_address` 为准，写入、查询与移除统一做去首尾空白加全小写规范化；数据库建立规范化地址唯一索引（`UNIQUE`），并发写入幂等；严格校验标准邮箱格式，服务端拒绝空串、纯空白、多地址、含控制字符/CRLF或损坏报头；前端放行优先提交邮件 UUID 由后端提取结构化地址，禁止客户端自报或从展示文本/Reply-To 自行截取。
- 邮件详情接口在附件列表（`AttachmentOut`，含普通文件附件与正文内联图片附件）中返回 `content_id` 及内联图片的短期预览签名参数。
- CID 正文内联图片 Signed URL 架构与安全处理规范：
    - **独立预览端点与鉴权解耦**：服务端独立挂载专用预览路由 `/api/mail/attachments/{id}/preview`，仅凭有效的预签名 Token 放行并流式返回二进制，**不依赖也不回退到 Cookie 会话认证**（沙箱 iframe 无 Cookie 亦可正常流式加载）。常规附件下载接口 `/api/mail/attachments/{id}` 继续保持现有 Cookie 认证与 CSRF 校验不变；
    - **HMAC-SHA256 确定性签名**：服务端使用配置注入的高熵密钥（跨实例一致，禁止硬编码），确定性序列化绑定 `version`、`purpose=inline-image-preview`、`attachment_id`、`issued_at`、`expires_at`；默认有效期 15 分钟；服务端使用常量时间比对（Constant-time comparison）；仅允许 GET / HEAD 只读方法；
    - **安全位图白名单（排除 SVG）**：仅允许 `image/png`, `image/jpeg`, `image/gif`, `image/webp` 4 种安全位图，明确**排除 `image/svg+xml`** 及一切可执行/脚本化 MIME；服务端根据文件头魔数真实核对 MIME；响应头强制附带 `X-Content-Type-Options: nosniff` 和 `Content-Disposition: inline`；
    - **后端防滥用保护**：无效、篡改或过期 Token 在访问数据库/解密前快速拒绝（401/403）；超时快速终止；单邮件内联图签发数量有界上限；流式解密复用现有完整性校验与内存有界临时文件机制；
    - **凭据脱敏**：带 Token 的正文仅在前端渲染时动态合成，**不入库持久化**；服务端访问日志、APM 与客户端错误上报对 `token` 参数自动脱敏。
- 精确 CSP 与沙箱安全基线：
    - 维持 `iframe sandbox` 不变：严禁为内联图片或附件访问给 iframe 增加 `allow-same-origin` 和 `allow-scripts`；
    - 未放行远程图片时，正文 CSP 精准限制为：`img-src /api/mail/attachments/ data:;`，**严禁放开全局 `http:` 或 `https:`**；外部远程外链图片依然被 CSP 严格拦截并展示提示条；放行后 CSP 才开放全局 `http: https:`；
    - 正文整体送入现有 DOMPurify 净化流水线清洗输出 `sanitizedHtml`，再注入 iframe。
- 远程图片识别边界：
    - 在 DOMPurify 清洗后的 DOM 结构中识别远程图片；
    - 匹配范围包括：`img[src]` 属性（包含 `http:`, `https:`、协议相对路径 `//` 以及属性前后空白）；
    - 样式内背景图等不支持在提示条放行的资源，由 CSP 严格阻断，作为保守安全降级。
- CID 规范化算法与碰撞降级：
    - URL 端规范化：剥离 `cid:` 前缀，进行严格单次百分号解码（`decodeURIComponent`）后小写；
    - 报头端规范化：剥离首尾尖括号 `<...>` 与空白后小写（不进行二次百分号解码）；
    - 空 ID、非法 `%` 编码、超长截断（>255 字符）或多个正文内联图片附件匹配冲突时安全降级原样，不猜测映射；非受控格式（如 SVG 或非图片）不签发预览 Token，安全降级保持原样。
- 放行请求与缓存撤销竞态控制：
    - 放行请求必须由服务端确认持久化成功后才放开远程图片加载；失败时保持拦截、提示错误并允许重试；请求未完成时切换邮件，即时作废旧请求；
    - 邮件详情返回「当前邮件是否已放行」；阅读器以此决定是否加载远程图片与是否展示拦截提示；
    - 拦截提示提供「仅此邮件允许加载」与「总是允许来自此发件人的图片」两个操作；后者仅在发件人地址可解析为有效邮箱时提供；
    - 放行成功后，当前阅读器立即以全新邮件正文文档重新渲染并开始加载图片，无需用户手动刷新页面；
    - 设置页提供已允许发件人的查看与移除；移除后即时阻断在途旧请求，相关邮件缓存立即进入重新校验/阻断状态，当前会话重新打开相关邮件即恢复拦截，未取得新权威结果前不渲染旧放行正文；撤销发件人白名单不覆盖单封放行记录。
- 修复单信深色视图覆盖（`viewModeOverride`）生命周期：
    - 状态提升至应用级全局内存 store（`mailStore`），采用按邮件 key 的字典映射（`Record<string, 'smart' | 'original'>`）并函数式更新；
    - 跨阅读器挂载保留（支持切信返回、设置页往返），但在页面刷新（重新加载应用）时重置。仅在当前前端内存隔离，不入库持久化。
- 数据库迁移、后端接口与前端 OpenAPI 契约同步更新。

### 非范围

- 单信深色视图覆盖（`viewModeOverride`）入库持久化（按前端全局内存会话独立保留即可，不增加数据库存储负担）。
- 域名级、图片托管域名级或全局「总是加载所有图片」白名单。
- 单封邮件放行的撤销界面；该记录仅在邮件删除时级联清理，发件人白名单可单独移除。
- 修改 DOMPurify 清洗规则、CSP 指令集合或 iframe `sandbox` 安全基线（不引入 `allow-scripts` 或 `allow-same-origin`）。
- 浏览器本地存储作为放行权威来源；本 task 明确改为服务端持久化。
- 普通文件附件（非内联附件）的免 Cookie 签名预览。
- SVG 格式内联文件的 Signed URL 预览（为防范 XSS 纵深防御，SVG 暂不纳入预览端点，用户可在附件列表正常下载）。
- 迁移降级时已保存放行记录的保留（降级删除放行表会清空已保存的放行偏好，此为预期回退代价；已有邮件与附件数据完全不受损）。

- [ ] AC-001：默认情况下，含 http(s) 或协议相对 `//` 远程图片的 HTML 邮件不加载图片并显示拦截提示；不含远程图片的 HTML 邮件不显示提示；纯文本或仅含有效内联图片的邮件不显示提示。
- [ ] AC-002：点击「仅此邮件允许加载」后，当前邮件无需手动刷新即以全新正文文档重建重新渲染并开始加载远程图片，拦截提示消失。
- [ ] AC-003：单封邮件放行后，重新登录/认证、刷新网页或在新浏览器会话中重新打开该邮件，图片仍直接加载且不显示拦截提示。
- [ ] AC-004：单封邮件放行仅作用于该邮件；切换到其他未放行邮件仍拦截，切回已放行邮件仍直接加载。
- [ ] AC-005：点击「总是允许来自此发件人的图片」后，当前邮件立即加载；同一发件人地址（大小写与首尾空白归一化后相同）的其他邮件在刷新或新浏览器会话中不再显示拦截提示并直接加载图片。
- [ ] AC-006：发件人放行严格基于结构化 `from_address` 规范化（去首尾空白与小写）；服务端拒绝空串、纯空白、多地址、含控制字符/CRLF或损坏报头；非法地址界面不展示该操作。
- [ ] AC-007：设置页展示已允许发件人并支持移除；移除后即时阻断在途旧请求，当前会话重新打开该发件人的已缓存邮件立即恢复拦截；若该邮件另有单封放行记录则仍放行。
- [ ] AC-008：删除邮件后，其单封邮件放行记录随数据库级联清理且不残留；删除邮件不影响发件人放行记录。
- [ ] AC-009：放行状态变化不改变安全基线：未放行邮件的 CSP 图片源仅允许自身内联预览端点与 `data:`，不放开远程外链 `http(s):`，iframe `sandbox` 不含 `allow-scripts` 或 `allow-same-origin`，DOMPurify 过滤规则不变。
- [ ] AC-010：服务端对不存在的邮件返回未找到；重复放行同一邮件或同一发件人在并发请求下均为幂等成功，数据库建立唯一约束；Cookie 会话写请求沿用现有 CSRF 校验，合法 API Key 保持现有免 CSRF 行为。
- [ ] AC-011：邮件详情返回的放行标志与实际记录一致：单封邮件记录命中或发件人记录命中任一成立即为已放行，两者均不命中即为未放行。
- [ ] AC-012：发件人白名单跨全部收件账号生效：同一地址在任一账号的邮件中放行后，其他账号中来自该地址的邮件同样直接加载；大小写或首尾空白不同的同一地址被视为同一条记录，移除时同样命中且列表中不出现重复项。
- [ ] AC-013：放行请求在服务端确认保存前不发起远程图片请求；请求失败时保持拦截并显示错误提示，用户可重试；切信即时取消在途请求，不把放行状态带到其他邮件。
- [ ] AC-014：默认拦截远程图片时，含匹配 Content-ID 附件的受控位图（PNG/JPEG/GIF/WebP）通过 Signed URL 在沙箱 iframe 内正常流式加载并解码显示（`naturalWidth > 0`）；非受控格式（如 SVG）、缺失/非法 Token 安全降级，不阻塞正文渲染及其他内联图；若邮件仅含有效内联图，不显示拦截提示；普通文件附件绝不发起自动请求。
- [ ] AC-015：CID 规范化（URL 单次百分号解码、报头去首尾尖括号与空白、小写匹配）；空 ID、非法 `%` 编码、超长截断标识或多个正文内联图片附件匹配冲突时安全降级原样。
- [ ] AC-016：内联图片预览端点（`/api/mail/attachments/{id}/preview`）仅凭有效 HMAC 签名 Token 放行，在沙箱 iframe 无 Cookie 环境下成功返回图片流；篡改、过期或伪造 Token 拒绝请求；响应头包含 `X-Content-Type-Options: nosniff`；全流程在放行前父页面与子 iframe 零跨域外部网络请求；带 Token 的正文不入库持久化。
- [ ] AC-017：在深色模式下，对邮件 A 切换单信原样/深色覆盖后，切换至邮件 B 或进入设置页再返回，邮件 A 的覆盖状态依然保留；刷新应用重置为全局偏好；未单独覆盖的邮件遵循全局深色偏好。
- [ ] AC-018：全链路真实数据库、Cookie 会话与 Signed URL 内联图片数据流端到端贯通，在 Chromium 与 WebKit 双浏览器中验证远程图片放行与 CID 正文内联图片渲染解码（`naturalWidth > 0`）。

## 上下文区

- 来源：`p066`（2026-10-30 核实：`MessageReader` 使用组件局部单值 `useState`，iframe key 未含放行状态，后端无放行存储；用户确认两类放行均入库）；`p067`（`cid:` 内联图片未映射，已并入本 task 闭环）；`p068`（`viewModeOverride` 单值标量覆盖多邮件互相冲掉，已并入本 task 闭环）。
- 技术发现：`docs/findings/d002_sandbox_iframe_omits_cookies_for_cid_attachments.md` 验证沙箱 iframe 不带同站 Cookie，确立内联图片不能直接复用普通 Cookie 认证接口，促成 Signed URL 免 Cookie 预览方案。
- 开源客户端实现参考（Cypht, Zero, SnappyMail, Thunderbird, Mailspring）：
    - 桌面原生/Electron 类（Thunderbird, Mailspring）：依赖私有协议栈（`cid:` / `mailspring://`）或直接读取磁盘文件流，绕开 Web 跨域 Cookie；
    - 现代 Webmail 类（Zero / Mail-0, SnappyMail）：因沙箱隔离禁止 Cookie，业内形成两大派系——方案 A（Zero 采用的父页面/解析器转 Base64 Data URL 注入）与方案 B（SnappyMail 采用的后端生成短期签名 Token 链接流式拉取）；
    - 传统 Webmail（Cypht）：因缺失有效 CID 映射链路导致 Issue #2134 碎图缺陷。
- 架构决策：经方案权衡与 Codex 审查评估，正式采纳 **方案 B（Signed URL）**，以无状态短期 HMAC 签名链接消除前端 Base64 内存开销，同时守住 `iframe sandbox` 与位图白名单（排除 SVG）安全边界。

### 有意不测

- 第三方广告拦截插件对图片的拦截：不受应用控制，使用本地测试图片服务器验证应用自身行为。
- 缺少 Content-ID 且无法唯一对应附件的非标 cid 图片：保持原样，不做猜测性映射。
- 域名级与全局放行：未定义产品语义，本 task 不覆盖。

### 测试策略

- 后端 PostgreSQL 集成测试：两类放行记录的写入、并发重复写入唯一约束与幂等、大小写与空白规范化真值表、跨账号全局命中、详情标志计算、非法/控制字符/CRLF 发件人拒绝、邮件删除级联与发件人白名单独立保留；迁移升级与降级。
- 后端 API 契约与安全测试：
    - `AttachmentOut` 暴露 `content_id` 及预览签名参数；
    - HMAC 签名生成与时间戳校验、常量时间比对、Token 篡改拦截、15 分钟过期拦截；
    - 独立预览端点无 Cookie 携带下的请求成功测试；

### 风险与回退

- 风险：Signed URL 为短期 Bearer 凭据，存在有界泄露窗口；本 spec 绑定单附件 UUID、限定只读预览且 15 分钟失效，日志脱敏且不入库持久化，风险完全可控。
- 风险：用户停留在同一封邮件超过 15 分钟导致 Signed URL 自然过期；重新切换邮件或刷新时会重新获取新 Token，正文平滑恢复。
- 风险：已有用户此前在浏览器会话内临时放行的邮件在本变更后需要重新放行一次；属于预期的语义升级。
- 风险：历史未存储 Content-ID 的老邮件无法按 ID 匹配；保持安全降级原样。
- 风险：发件人地址规范化与展示不一致；由服务端收敛负责标准邮箱校验与规范化，客户端优先提交邮件 UUID。
- 风险：撤销白名单后未使已缓存详情失效，staleTime 内继续放行；以撤销即时阻断在途响应与重新校验测试覆盖。
- 风险：放行 API 尚未确认持久化就乐观放开图片，失败后远程请求已泄露访问事实；以失败分支的请求计数测试覆盖。
- 回退：撤销发布后执行迁移降级删除两张新增表即可；`AttachmentOut` 字段向后兼容，不改动既有数据；降级将清除已保存的用户放行偏好，邮件本体不受影响。

### 依赖与约束

- 需要新增 Alembic 迁移与重新生成 OpenAPI TypeScript 契约。
- 不引入新的第三方依赖；沿用现有认证、CSRF、PostgreSQL 事务及 Python 标准库 / `itsdangerous` 签名设施。
- 放行记录属于隐私边界变更：只有用户显式操作且服务端持久化成功后才写入并放开图片，默认拦截行为与 CSP/sandbox 基线不得放宽。
- 内联图片预览端点严禁引入 `allow-same-origin`。
