# Task spec

## 背景

p073 记录一起生产慢刷新：邮件于 22:15:55 CST（14:15:55Z）到达服务端，用户 22:15:58 CST 在收件箱点「立即同步」，邮件 14:16:50Z 才落库，请求 14:16:53Z 才终态（55s）。原因不是邮件慢，而是账号级手动 delta 先做文件夹发现（12.5s），随后把 8 个文件夹的 delta 以同一优先级入队，由账号租约串行执行；收件箱排第 6，前端与用户都要等其余文件夹。后台 patrol/周期任务同时占用连接槽放大了等待。

本 task 只调整账号内文件夹之间的调度次序：收件箱的增量/基线任务在同账号其他文件夹之前被认领，并让 delta 与 metadata 在各类重新排期路径中保持原任务优先级。同步范围与“等待全部文件夹完成后请求终态”的现有语义不变。

注意调度判据：`WorkerJob.created_at` 是 `server_default=func.now()`，同一事务内入队的所有子任务 `created_at` 相同；`ORDER BY priority, created_at` 在并列时顺序不确定。因此收件箱优先必须通过“priority 数值严格更小”保证，不能依赖入队循环顺序或 provider 返回顺序。

## 契约区

### 范围

- 账号级 delta 同步在文件夹发现后入队的增量任务中，收件箱（`role="inbox"`）任务的 priority 数值严格小于同账号其他文件夹任务，并在同账号无在途文件夹任务时先被认领、先完成。
- 无已完成基线的账号初始化路径中，收件箱的基线（metadata）任务 priority 数值严格小于同账号其他文件夹 metadata 任务，并在同账号无在途文件夹任务时先被认领、先完成；分页续页保持该优先级。
- delta 因账号租约占用、限流、连接预算不足、临时 provider 错误、fencing 冲突或分页未耗尽而重新排期时，后续任务保持原任务的 priority。
- metadata 因账号租约占用、限流、连接预算不足或分页未耗尽而重新排期时，后续任务保持原任务的 priority；cursor-invalid 重建沿用现有显式 40，不因本 task 降低。
- 账号不存在 `role="inbox"` 文件夹时，不产生收件箱优先任务，现有优先级与行为不变。
- 同步请求仍在账号内全部文件夹任务结算后才进入终态；手动/设置页/批量入口的同步范围不变。

### 非范围

- 不抢占已在执行（CLAIMED）的同账号任务：账号租约下，收件箱只能等当前在途任务结束，不承诺任意时刻立即切换。
- 不缩短 Graph `list_folders` 的多请求耗时，不跳过或缓存文件夹发现。
- 不改变前端「立即同步」按钮的等待语义、SSE 失效机制或列表视图范围。
- 不调整收件箱定时轮询间隔、IDLE 配额、连接槽预算或其他 job 类型的全局优先级分层。
- 不优先于全局更高优先级任务：按需正文（10）、`remote_operation_push`（40）、cursor-invalid 重建（40）仍在收件箱 delta/metadata 之前。
- 新发现或复活文件夹（A320）的 metadata（50）仍可能排在收件箱 delta（55）之前；本 task 不改变该跨任务类型次序。
- `sync_account_folders` 自身的容量/限流重排优先级不在本 task 内（p073 未触发该路径）。
- 不为用户新增优先级配置项。

## 上下文区

- 来源：p073（2026-11-04 生产证据；根因已定位为账号级文件夹发现后的 delta 入队顺序与租约串行，非邮件服务器慢）

### 有意不测

- 真实 Outlook/Graph 网络时延与账号限流：不可控且与调度次序无关；用可控延迟的测试 provider 覆盖。
- 前端旋转动画与列表渲染时序：现有 `useMailCoreRealtime` 测试已覆盖 `message.upserted` 触发失效；本 task 不改前端。
- CLAIMED 任务的抢占：账号租约设计不提供抢占；测试只构造 pending 任务队列。

### 测试策略

- 后端集成测试（多文件夹夹具 + 可控延迟测试 provider）：收件箱在 provider 返回顺序中故意置后；断言收件箱任务 priority 数值严格小于其他文件夹（不能只断言认领顺序，因同事务 `created_at` 并列），并断言收件箱先被认领、先完成，完成时邮件已落库。
- 无基线夹具：断言 metadata 任务 inbox priority 严格最小；构造多页 metadata，断言续页 priority 仍为 inbox 值。
- `sync_folder_delta` 单元测试：外部持有账号租约、注入限流、容量不足、provider 临时错误、fencing 冲突和未耗尽分页，断言重新入队任务 priority 等于原任务 priority。
- `sync_folder_metadata` 单元测试：外部持有账号租约、注入限流、容量不足和未耗尽分页，断言续页/重排任务 priority 等于原任务 priority；cursor-invalid 重建仍为 40。
- 优先级传播边界测试：后台周期 inbox delta（75）重排后仍为 75；文件夹级手动 delta（20）重排后仍为 20；直接调用 `sync_folder_delta`/`sync_folder_metadata` 不传 priority 时保持现有默认值。
- 无 `role="inbox"` 夹具：断言不产生 inbox 特优任务、同步正常完成。
- 同步请求聚合测试：多文件夹同步在全部子任务结算前保持非终态，全部结算后才终态。
- 全量回归：相关 `tests/mail_core/test_sync_mode_policy.py`、`test_sync_delta.py`、`test_sync_retry_queue.py`、`test_worker_loop.py` 与新增测试。

### 风险与回退

- 风险：priority 是全局数值，收件箱 55/45 不仅排在同账号普通 delta/ metadata 之前，也会排在其他账号普通 delta（60）之前；“仅在同账号内提高次序”只是相对效果，跨账号副作用可接受但需知悉。
- 风险：保持原优先级会改变现有重排行为——后台周期 inbox delta（75）不再在重排时升到 60，文件夹级手动 delta（20）不再回落到 60。两项均为修正，但需各补一条测试防止回归。
- 风险：频繁手动刷新可能让同账号其他文件夹 delta 长期排在收件箱之后；账号租约与去重键会把并发收件箱任务收敛为单条在途任务，且每个请求仍会为全部文件夹入队，测试覆盖“一次请求内全部文件夹最终完成”。
- 风险：metadata 续页保持 inbox 优先级会提高该链的调度权重；默认参数保持 50，仅由 handler 传入原任务优先级，影响面限定在 metadata 重排路径。
- 回退：还原 `sync/engine.py` 的入队优先级与 `sync/delta.py` 的优先级参数即可，无数据库迁移、无接口契约变更。

### 依赖与约束

- 无前置 task；不改 schema、OpenAPI 或用户可见配置。
- priority 是跨账号的全局数值，而不是账号内局部权重；实现需接受前述跨账号副作用。
- 现有全局优先级分层（按需正文 10、写回 40、metadata 50、delta 60、周期轮询 75 等）保持不变，仅在“同账号文件夹之间”提高收件箱次序。
- 账号租约保证同账号同时只有一个文件夹任务执行；收件箱优先级只在 pending 队列内生效，无法抢占 CLAIMED 任务。
- 无 `role="inbox"` 的账号（部分 IMAP 目录无法映射角色）必须回退为现有行为，不得报错或制造空优先任务。
