## 一、 产品边界与长期排除项决策

以下条目已由产品与架构方案明确锁定，确认为当前阶段不予处理或超出产品范围的设计：

1. **单用户能力凭据模型 (Single-user & Capability-based UUID)**：

    - **裁决**：单登录密码保护实例，无多租户、用户角色或行级 ACL；Bearer API Key 具备同等全量权限。
    - **理由**：在此单用户边界内，资源 UUID（邮件、附件、账户等）即能力凭据（Capability），知晓 UUID 即获 API 访问权限，不得作为多租户防 IDOR 缺陷处理。

2. **永久废弃浏览器扩展 (No browser extension - wontfix)**：

    - **裁决**：永久不发布浏览器扩展；原 `browser-extension/` 目录与 `/api/extension/*` 桥接已彻底废弃并移除，禁止重新引入。

3. **移除多皮肤系统 (No system skins)**：

    - **裁决**：彻底移除 Flask 时期的外部皮肤包与模板系统（`data/skins/` 目录）；外观严格限定为 SPA 内置的亮色、暗色及跟随系统主题。

4. **产品不含发信与联系人 (No sending & contacts)**：

    - **裁决**：产品核心聚焦于收信与多账号聚合阅读，明确不包含撰写 (compose)、回复 (reply)、转发 (forward)、联系人管理及发信系统通知；前端 SPA 不提供写信界面。

5. **平台打包未签名维持现状 (Desktop packaging signature & notarization)**：

    - **裁决**：macOS (dmg) 与 Windows (nsis) 当前为自托管未签名构建，暂不实施商业代码签名、公证及应用商店上架适配，维持当前打包现状。

6. **暂不开放多文件夹/多目录 API (Folders limitation)**：

    - **裁决**：后端同步全量文件夹，但 HTTP API 仅暴露各账户及统一收件箱 (`/api/mail/inbox`)，前端侧栏维持收件箱极简扁平视图。
    - **决策原因与暗坑**：
        1. **同步配额爆炸**：若开放全量文件夹浏览与后台增量轮询，拥有数十个文件夹的账户极易触发 Gmail / Graph 的速率限制 (Rate Limit)；
        2. **标签映射混乱**：Gmail 单封邮件可同时被打上多个 Label，在文件夹树中会导致同一邮件多处展示、重复计数及操作心智割裂；
        3. **移动端交互妥协**：侧边栏目前为 760px 响应式极简设计，引入深度嵌套树会导致窄屏下的导航与滚动体验退化。

7. **暂不开发归档与跨目录移动 (Archive, junk and move)**：

    - **裁决**：维持当前仅支持废纸篓/删除（Trash，本地优先 + 异步远程入队）的现状，暂不开发归档 (Archive)、垃圾邮件 (Junk) 及跨文件夹移动 (Move)。
    - **决策原因与暗坑**：
        1. **异构 Provider 语义根本性冲突**：Gmail 的归档与移动实质是“打/剥离标签”（无物理移动）；Graph 移动邮件后其远程 `message_id` 会发生改变；IMAP 移动邮件则会彻底销毁旧 UID 并分配新 UID，且大量私有邮件服务商缺失标准的 `\Archive` 特殊文件夹；
        2. **增量同步状态断裂风险**：远端 ID/UID 的突变若处理不慎，极易导致增量同步将其误判为全新邮件重复拉取，或残留幽灵本地数据。

## 二、 架构演进与安全技术决策

### 2026-10-21: 方案 A - 认证密码与会话状态统一入库

- **背景**：此前 Compose 部署修改密码仅修改进程内存缓存，容器重启后回退至环境变量旧密码；且会话版本号在多进程模式下无法共享。
- **决策**：创建 `auth_credentials` 表（迁移 `20261021_0012` 与 `0013`），将登录密码 bcrypt hash 与全局 `session_epoch` 统一持久化至 PostgreSQL。
- **结果**：环境变量仅作为全新安装首启的 bootstrap 数据源；一旦数据库初始化完成，密码以数据库为权威源，API 改密直接写库，彻底解决重启回退问题；改密与登出跨进程即时吊销旧 Session。

### 2026-10-21: IMAP 删除安全阻断策略

- **背景**：部分旧 IMAP 服务器缺少 `UID MOVE` 或 `UIDPLUS` 能力，旧代码回退执行 `STORE \Deleted` + `EXPUNGE`，RFC 3501 规定其清空当前目录下全部待删除邮件，造成连带误删风险。
- **决策**：执行绝对安全策略——优先调用 `UID MOVE` 移入废纸篓；若不支持或移动失败，**严禁调用全邮箱 `c.expunge()`，且不要打 `\Deleted` 标记，直接向调用方报错返回失败**（提示当前 IMAP 服务器不支持安全删除）。
- **结果**：100% 杜绝因其他客户端打标未清空而造成的连带误删。

### 2026-10-21: 历史泄露凭据资产处置

- **背景**：公开历史 commit `34c81310` 遗留 Outlook 账号密码与 Token。
- **决策**：经溯源确认为上游原仓库 `assast/outlookEmail`（作者 `luekongbai`）在 2026-01-13 的首个初始化提交，系上游原作者历史测试资产。本仓库不执行破坏性 Git 历史重写（避免 fork 分叉与破坏下游 clone），在安全审计基线中将其标记为上游遗留已知资产，并指导外部撤销。

### 2026-10-21: 前端长列表游标分页与未读角标

- **背景**：此前 SPA 列表硬编码仅展示 100 封，侧边栏角标直接基于本地缓存第一页推导，超出 100 封时未读数少报。
- **决策**：
    1. 后端提供 `/api/mail/stats` 全局未读聚合端点，侧边栏单次请求直接读取全局及各账户真实未读计数；
    2. 邮件列表迁移为 TanStack React Query 的 `useInfiniteQuery`，结合后端的 Keyset 游标分页提供“加载更多”按钮，实现深翻页；
    3. 重构缓存更新器以同时适配普通数组与 `InfiniteData` 结构，彻底解决删除邮件导致的列表归零闪烁问题。
