# Task spec

## 背景

当前新邮件发现完全依赖 t057 的服务端周期轮询：收件箱默认 20 分钟才被检查一次，新邮件端到端延迟上限即一个轮询周期；19bc2b76 移除客户端即时同步后，不再有任何更快的发现通道。2026-10-28 的同类产品拉取策略对比（Cypht / Zero / SnappyMail / Thunderbird / Mailspring）显示：IMAP 生态的主流实时机制是 IDLE（RFC 2177）——客户端在收件箱上维持一条长连接，服务器有变化时主动下发未标记响应，客户端随即做增量同步；Thunderbird 与 Mailspring 均以 IDLE 为收件箱实时通道、轮询为兜底。kkmail 的账号构成以 IMAP 为主（Gmail 走 IMAP 应用专用密码、163、QQ 等），IDLE 无需任何第三方云设施即可覆盖，且长连接常驻比周期性反复登录对服务商风控更友好。本 task 为 IMAP 账号接入 IDLE 收件箱监听，把收件箱新邮件延迟从分钟级降到秒级，t057 轮询保留为兜底与安全网。

## 契约区

### 范围

- 在 Worker 侧新增 IDLE watcher 组件：对每个符合条件的 IMAP 账号维持至多一条长连接，SELECT 其收件箱（`role="inbox"`）后进入 IDLE；仅对已完成基线（`full_scan_complete`）的文件夹启用。
- IDLE 只作唤醒信号：收到服务器未标记响应（EXISTS / EXPUNGE / FETCH 等表明收件箱有变化）后，结束本轮 IDLE 并为该文件夹入队既有 `SYNC_FOLDER_DELTA`（沿用既有去重键 `delta:{account}:{folder}`）；邮件内容拉取、落库、删除对账全部仍走既有 delta / reconcile 管线。
- 连接生命周期管理：服务器侧 IDLE 超时（约 29 分钟）前主动 DONE 并重新进入 IDLE；连接断开后以带随机抖动的指数退避重连，多账号同时断线时重连时刻被打散，不形成集中登录风暴。
- 能力门控：仅当服务器在 CAPABILITY 中宣告 IDLE 时启用；不宣告的账号不建立长连接，完全维持 t057 轮询行为。
- 连接预算治理：IDLE 长连接纳入既有全局连接预算（`connection_slots`，上限 8、前台保留 0–1）统一核算，不得挤占前台保留槽位；预算不足时按账号降级为纯轮询。
- 启停跟随账号状态：账号 `sync_enabled=false`、凭据变更或失效、收件箱变为 paused 时关闭对应 IDLE 连接且不再重连；条件恢复后自动重新建立。
- 配置纳入 t058 集中式配置：提供 IDLE 全局开关与关键参数（重连退避基数等），关闭开关即回到纯轮询模式。
- watcher 状态（idling / backoff / fallback 等）经既有账号同步状态面可观测；watcher 自身异常不得把账号误标为永久 failed。

### 非范围

- 不为非收件箱文件夹建立 IDLE 连接（每账号至多一条）；非收件箱的周期发现由 t060 负责。
- 不接入 Microsoft Graph change notifications（Outlook 推送），不在本 task 范围。
- 不接入 Gmail API `users.watch` / Pub/Sub（Gmail API 引擎已下线，不复活）。
- 不移除、不弱化 t057 周期轮询：轮询继续作为 IDLE 不可用、断线间隙与非收件箱文件夹的兜底。
- 不复活任何客户端触发同步（19bc2b76 的移除结论不变）。
- IDLE 路径不直接读写邮件数据，不绕过基线门禁、账号租约与 fencing。

### 验收标准

只写可观察、可独立验证的行为；每条使用稳定且不复用的 `AC-NNN`。需真实部署或人工环境验证时在编号前加 `[deploy]`。技术选型不作为行为 AC。

<!-- /规范 -->

- [ ] AC-001：对启用（`sync_enabled=true`）、收件箱已完成基线、且服务器宣告 IDLE 能力的 IMAP 账号，Worker 建立并维持一条只 SELECT 收件箱的 IDLE 长连接；服务器不宣告 IDLE 时不建立连接，该账号行为与现行 t057 轮询完全一致。
- [ ] AC-002：IDLE 期间收件箱有新邮件到达（服务器下发未标记响应）后 10 秒内，该文件夹的 `SYNC_FOLDER_DELTA` 被入队并执行，新邮件落库，不等待 20 分钟轮询到期。
- [ ] AC-003：IDLE 连接被服务器超时关闭或网络中断后，watcher 以带随机抖动的退避自动重连并恢复 IDLE；多个账号同时断线时，各账号的重连时刻被打散，不在同一时刻集中发起登录。
- [ ] AC-004：IDLE 路径只产生唤醒与入队动作：全部邮件拉取与落库仍经既有 delta / reconcile 管线（去重键、账号租约、fencing、基线门禁均不变），IDLE 代码路径不直接写 `messages` / `message_bodies`。
- [ ] AC-005：任意时刻，全部 IDLE 长连接与既有同步连接之和不超过全局连接预算上限，且 IDLE 不占用前台保留槽位；预算不足时对应账号降级为纯轮询，手动同步与前台请求不受阻塞。
- [ ] AC-006：账号被禁用、凭据变更或失效、收件箱变为 paused 时，对应 IDLE 连接被关闭且不再重连；条件恢复后自动重新建立并恢复秒级发现。
- [ ] AC-007：watcher 组件异常退出或单账号 IDLE 循环反复失败时，Worker 主任务循环与 t057 巡检调度不受影响，该账号自动退化为轮询发现且不被误标为永久 failed。
- [ ] AC-008：IDLE 全局开关与重连退避等关键参数纳入集中式配置（t058 体系）可调；关闭开关后全部账号回到纯 t057 轮询模式，无残留长连接。
- [ ] [deploy] AC-009：在真实 IMAP 服务（163 或 Gmail 任一）部署环境实测：向被监听账号发送一封新邮件，30 秒内该邮件在本地库可见。

## 上下文区

- 来源：用户确认的同步策略对比结论（2026-10-28，五家开源邮件应用拉取策略与 kkmail 对比）；相关历史条目 p047（新邮件收取时延，已归档，其客户端触发部分已被 19bc2b76 否决，本 task 只取其「降低外部服务器→后端段延迟」的问题定义）

### 有意不测

- 真实服务商的大规模长连接压测（如 300 账号同时 IDLE 的服务商侧限流表现）：本地以 fake IMAP 服务器与 mock provider 验证连接治理与重连打散逻辑，真实规模表现经 AC-009 的单账号实测与上线后观测覆盖。

### 测试策略

- 单元测试：fake IMAP 连接对象模拟 CAPABILITY 宣告、IDLE 未标记响应、服务器超时关闭与断线，验证唤醒入队、退避打散、能力门控与状态跟随。
- 集成测试：mock provider + 本地 DB 夹具，验证 IDLE 唤醒后 delta 落库全链路、预算不足降级、watcher 异常不影响巡检调度。

### 未知契约清单

<!-- 规范（门禁必留，不得删除） -->

未核实的外部契约标为 `UNVERIFIED-BLOCKING` 或 `UNVERIFIED-SPIKE`；核实后改写为结论和验证方式。无则写“无”。

<!-- /规范 -->

- 各服务商 IDLE 细节差异（163 需先发 IMAP ID 命令、单 IP 长连接总数的实际限流阈值、各家 IDLE 超时时长）：UNVERIFIED-SPIKE，实现期以 fake 服务器覆盖协议行为，真实服务商差异经 AC-009 实测与部署观测核实，不阻断 backlog。
- 现行 IMAP provider 所用客户端库是否提供可用的 IDLE 原语（长连接阻塞读、DONE 打断）：UNVERIFIED-SPIKE，实现期先行核查；若库不支持，允许在 provider 内部以既有连接抽象补齐 IDLE 原语，但不得改变 provider 对其他同步路径的契约。

### 风险与回退

- 风险：常驻长连接与既有 8 槽位预算的 contention；单一出口 IP 上长连接总数触发服务商隐形限流；watcher 生命周期管理不当导致连接泄漏或重连风暴。
- 防御：AC-005 的预算统一核算与降级、AC-003 的抖动退避、连接数与状态可观测。
- 回退：集中配置关闭 IDLE 开关即全量回到 t057 纯轮询；或 git revert 对应 commit。

### 依赖与约束

- 依赖 t057（周期巡检调度，已完成）与 t058（集中式配置，已完成）。
- 必须遵守既有约束：paused 文件夹跳过规则（p060 / A321）、checkpoint 写入 fencing、账号租约串行化。
- 与 t060 同改 Worker 调度与连接面，无硬依赖；排期时由 task-schedule 评估冲突，建议错开执行。
