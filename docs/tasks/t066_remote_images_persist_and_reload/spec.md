# Task spec

## 背景

用户打开含外链图片的 HTML 邮件时，点击「仅此邮件允许加载」后图片仍停留在占位状态；刷新网页后放行状态完全丢失，再次出现拦截提示；也无法将某个发件人的邮件图片设置为长期允许。`p066` 已核实代码事实：放行状态仅存于 `MessageReader` 组件局部的单值 `useState`，既未持久化也未集合化；邮件正文 iframe 的 React key 不包含放行状态；后端当前没有任何远程图片放行记录。另有确定缺陷：归档层已把 `Content-ID` 存入附件表，但附件 DTO 不返回，前端也从不把 `cid:` 图片重写为可访问地址，导致内联图片在默认拦截与放行后都无法显示（`p067` 并入本 task 闭环）。同时，`p068` 记录的同类位点 `MessageReader.tsx:82`（`viewModeOverride` 单信深色覆盖）同样采用单值标量 `useState`，导致切换多封邮件或进入设置页往返时覆盖设置丢失（`p068` 并入本 task 闭环，原历史 pending 中的范围排他描述在此统一更正）。用户已确认：单封邮件放行与发件人放行两类状态都必须入库持久化。无论浏览器是否会在 `srcdoc` 更新后重试图片请求，本 task 都在放行后强制重建正文文档；真实浏览器测试用于验收行为，不作为实施前提。

经前置架构与代码审查（Codex `gpt-6.1-sol`，审查意见：`CHANGES_REQUIRED`），本 spec 针对安全流水线顺序、资源预算、竞态一致性、发件人地址验证及双浏览器全栈验收做了深度加固。

## 契约区

### 范围

- 附件分类与下载边界定义（消除歧义，严格区分两类附件）：
    - **普通文件附件（`is_inline=false`）**：绝不自动下载。保持现有交互与架构不变，仅在用户于附件列表中显式点击时才触发下载或保存，不发起任何自动静默拉取，不受本 task 内联配额限制；
    - **正文内联图片附件（`is_inline=true` 且被正文 `<img src="cid:...">` 引用）**：属于邮件正文视觉排版不可分割的组成部分，由前端阅读器在渲染正文时，通过父页面带认证自动按需获取图片字节并转为 Base64 `data:` URL 替换对应 `cid:` 节点；
    - **自动拉取配额与预算适用范围**：本 task 中所有的资源配额约束（单图上限 ≤10 MiB、单邮件累计内联图内存预算 ≤20 MiB、最多 3 并发、超时 5s 等）**严格且仅适用于上述“正文内联图片附件”转 Base64 注入正文的自动处理，绝对不适用于普通文件附件**；
    - **超限降级边界**：超出上述安全配额阈值的正文内联图片附件，仅降级为正文对应位置不自动内联塞入（正文保留占位），该文件在附件列表中仍完整保留，用户需要时仍可在附件列表手动点击下载。
- 服务端持久化两类远程图片放行：按邮件（主键/外键关联 `mail_id`）、按发件人地址（服务端全局跨账号共享）。
- 发件人白名单服务端唯一权威与规范化：以服务端存储的结构化 `from_address` 为准，写入、查询与移除统一做去首尾空白加全小写规范化；数据库建立规范化地址唯一索引（`UNIQUE`），并发写入幂等；严格校验标准邮箱格式，服务端拒绝空串、纯空白、多地址、含控制字符/CRLF或损坏报头；前端放行优先提交邮件 UUID 由后端提取结构化地址，禁止客户端自报或从展示文本/Reply-To 自行截取。
- 邮件详情接口在附件列表（`AttachmentOut`，含普通文件附件与正文内联图片附件）中返回 `content_id`。
- CID 正文内联图片安全处理流水线与离线容器隔离：
    - 在无网络副作用的离线容器（如 `DOMImplementation.createHTMLDocument` 或离线 DocumentFragment）内解析正文，提取 `<img src="cid:...">` 节点；
    - 由父页面带认证按内联图片附件 UUID 获取图片数据；严格校验受支持的图片 MIME 类型（`image/png`, `image/jpeg`, `image/gif`, `image/webp`, `image/svg+xml`）并生成 Base64 `data:` URL；
    - 仅通过 DOM 属性 API（`setAttribute` / `.src`）修改 `img.src`；
    - 属性修改完成后，整体送入现有 DOMPurify 净化流水线清洗输出 `sanitizedHtml`，再注入 iframe。此后严禁任意 HTML 字符串拼装或二次改写；
    - 维持沙箱安全基线不变：严禁为内联图片或附件访问给 iframe 增加 `allow-same-origin`，亦不得依赖沙箱 iframe 发送会话 Cookie（已由 `docs/findings/d002_sandbox_iframe_omits_cookies_for_cid_attachments.md` 验证沙箱内不发同站 Cookie）。
- 正文内联图片资源预算与局部降级（仅针对正文内联图片自动注入，不影响普通文件附件）：
    - 资源配额：单张正文内联图片附件上限 10 MiB、单邮件累计正文内联图片内存预算 20 MiB、最多 3 并发请求、单请求超时 5s；
    - 同一正文内联图片附件 UUID 去重仅拉取一次；
    - 超限、404/401、请求超时、非法 MIME 或图片解码失败时局部降级（正文保留原占位或原样），不阻塞正文渲染及其他内联图，且该文件在附件列表中仍可手动点击下载；
    - 切信或阅读器卸载时通过 `AbortController` 立即中止未完成的在途正文内联图片拉取请求并释放内存引用。
- 远程图片识别边界：
    - 在 DOMPurify 清洗后的 DOM 结构中识别远程图片；
    - 匹配范围包括：`img[src]` 属性（包含 `http:`, `https:`、协议相对路径 `//` 以及属性前后空白）；
    - 样式内背景图等不支持在提示条放行的资源，由 CSP 严格阻断，作为保守安全降级。
- CID 规范化算法与碰撞降级：
    - URL 端规范化：剥离 `cid:` 前缀，进行严格单次百分号解码（`decodeURIComponent`）后小写；
    - 报头端规范化：剥离首尾尖括号 `<...>` 与空白后小写（不进行二次百分号解码）；
    - 空 ID、非法 `%` 编码、超长截断（>255 字符）或多个正文内联图片附件匹配冲突时安全降级原样，不猜测映射。
- 放行请求与缓存撤销竞态控制：
    - 放行请求必须由服务端确认持久化成功后才放开远程图片加载；失败时保持拦截、提示错误并允许重试；请求未完成时切换邮件，即时作废旧请求；
    - 邮件详情返回「当前邮件是否已放行」；阅读器以此决定是否加载远程图片与是否展示拦截提示；
    - 拦截提示提供「仅此邮件允许加载」与「总是允许来自此发件人的图片」两个操作；后者仅在发件人地址可解析为有效邮箱时提供；
    - 放行成功后，当前阅读器立即以全新邮件正文文档重新渲染并开始加载图片，无需用户手动刷新页面；
    - 设置页提供已允许发件人的查看与移除；移除后即时阻断在途旧请求，相关邮件缓存立即进入重新校验/阻断状态，当前会话重新打开相关邮件即恢复拦截，未取得新权威结果前不渲染旧放行正文；撤销发件人白名单不覆盖单封放行记录；
    - CID 异步注入严格绑定邮件 UUID 与正文/请求版本号，切信后晚到的内联图片响应直接丢弃，禁止串写。
- 修复单信深色视图覆盖（`viewModeOverride`）生命周期：
    - 状态提升至应用级全局内存 store（`mailStore`），采用按邮件 key 的字典映射（`Record<string, 'smart' | 'original'>`）并函数式更新；
    - 跨阅读器挂载保留（支持切信返回、设置页往返），但在页面刷新（重新加载应用）时重置。仅在当前前端内存隔离，不入库持久化。
- 数据库迁移、后端接口与前端 OpenAPI 契约同步更新。

### 非范围

- 单信深色视图覆盖（`viewModeOverride`）入库持久化（按前端全局内存会话独立保留即可，不增加数据库存储负担）。
- 域名级、图片托管域名级或全局「总是加载所有图片」白名单。
- 单封邮件放行的撤销界面；该记录仅在邮件删除时级联清理，发件人白名单可单独移除。
- 修改 DOMPurify 清洗规则、CSP 指令集合或 iframe `sandbox` 安全基线（不引入 `allow-scripts` 或 `allow-same-origin`）。
- 浏览器本地存储作为放行权威来源；本 task 明确改为服务端持久化。
- 迁移降级时已保存放行记录的保留（降级删除放行表会清空已保存的放行偏好，此为预期回退代价；已有邮件与附件数据完全不受损）。

### 验收标准

只写可观察、可独立验证的行为；每条使用稳定且不复用的 `AC-NNN`。需真实部署或人工环境验证时在编号前加 `[deploy]`。技术选型不作为行为 AC。

- [ ] AC-001：默认情况下，含 http(s) 或协议相对 `//` 远程图片的 HTML 邮件不加载图片并显示拦截提示；不含远程图片的 HTML 邮件不显示提示；纯文本或仅含有效内联图片的邮件不显示提示。
- [ ] AC-002：点击「仅此邮件允许加载」后，当前邮件无需手动刷新即以全新正文文档重建重新渲染并开始加载远程图片，拦截提示消失。
- [ ] AC-003：单封邮件放行后，重新登录/认证、刷新网页或在新浏览器会话中重新打开该邮件，图片仍直接加载且不显示拦截提示。
- [ ] AC-004：单封邮件放行仅作用于该邮件；切换到其他未放行邮件仍拦截，切回已放行邮件仍直接加载。
- [ ] AC-005：点击「总是允许来自此发件人的图片」后，当前邮件立即加载；同一发件人地址（大小写与首尾空白归一化后相同）的其他邮件在刷新或新浏览器会话中不再显示拦截提示并直接加载图片。
- [ ] AC-006：发件人放行严格基于结构化 `from_address` 规范化（去首尾空白与小写）；服务端拒绝空串、纯空白、多地址、含控制字符/CRLF或损坏报头；非法地址界面不展示该操作。
- [ ] AC-007：设置页展示已允许发件人并支持移除；移除后即时阻断在途旧请求，当前会话重新打开该发件人的已缓存邮件立即恢复拦截；若该邮件另有单封放行记录则仍放行。
- [ ] AC-008：删除邮件后，其单封邮件放行记录随数据库级联清理且不残留；删除邮件不影响发件人放行记录。
- [ ] AC-009：放行状态变化不改变安全基线：未放行邮件的 CSP 图片源仍仅允许 `data:` 与 `cid:`，iframe `sandbox` 不含 `allow-scripts` 或 `allow-same-origin`，DOMPurify 过滤规则不变。
- [ ] AC-010：服务端对不存在的邮件返回未找到；重复放行同一邮件或同一发件人在并发请求下均为幂等成功，数据库建立唯一约束；Cookie 会话写请求沿用现有 CSRF 校验，合法 API Key 保持现有免 CSRF 行为。
- [ ] AC-011：邮件详情返回的放行标志与实际记录一致：单封邮件记录命中或发件人记录命中任一成立即为已放行，两者均不命中即为未放行。
- [ ] AC-012：发件人白名单跨全部收件账号生效：同一地址在任一账号的邮件中放行后，其他账号中来自该地址的邮件同样直接加载；大小写或首尾空白不同的同一地址被视为同一条记录，移除时同样命中且列表中不出现重复项。
- [ ] AC-013：放行请求在服务端确认保存前不发起远程图片请求；请求失败时保持拦截并显示错误提示，用户可重试；切信即时取消在途请求，响应与 CID 注入严格绑定邮件 UUID 与请求版本，不把放行状态带到其他邮件。
- [ ] AC-014：在正文内联图片资源预算内（单张正文内联图片附件 ≤10 MiB、单邮件累计正文内联图片 ≤20 MiB）且为受控图片 MIME 的内联图片正常解码显示；超限、404、401、请求超时、非法 MIME 安全降级（正文保留占位，附件列表中仍可手动下载），不阻塞正文渲染及其他内联图；普通文件附件保持用户手动点击下载，绝不自动下载。
- [ ] AC-015：CID 规范化（URL 单次百分号解码、报头去首尾尖括号与空白、小写匹配）；空 ID、非法 `%` 编码、超长截断标识或多个正文内联图片附件匹配冲突时安全降级原样。
- [ ] AC-016：内联图片在无网络副作用的离线容器解析，通过父页面认证获取后仅以属性 API 修改为 Base64 data URL，随后统一经 DOMPurify 清洗输出；全流程在放行前父页面与子 iframe 零跨域外部网络请求；切信或卸载时中止在途正文内联图片拉取请求并释放引用。
- [ ] AC-017：在深色模式下，对邮件 A 切换单信原样/深色覆盖后，切换至邮件 B 或进入设置页再返回，邮件 A 的覆盖状态依然保留；刷新应用重置为全局偏好；未单独覆盖的邮件遵循全局深色偏好。
- [ ] AC-018：全链路真实数据库、Cookie 会话与正文内联图片数据流端到端贯通，在 Chromium 与 WebKit 双浏览器中验证远程图片放行与 CID 正文内联图片渲染解码（`naturalWidth > 0`）。

## 上下文区

- 来源：`p066`（2026-10-30 核实：`MessageReader` 使用组件局部单值 `useState`，iframe key 未含放行状态，后端无放行存储；用户确认两类放行均入库）；`p067`（`cid:` 内联图片未映射，已并入本 task 闭环）；`p068`（`viewModeOverride` 单值标量覆盖多邮件互相冲掉，已并入本 task 闭环）。
- 技术发现：`docs/findings/d002_sandbox_iframe_omits_cookies_for_cid_attachments.md` 验证沙箱 iframe 不带同站 Cookie，确立内联图片由父页面认证获取转 data URL 注入的设计约束。
- 架构与代码审查：Codex `gpt-6.1-sol` 结论 `CHANGES_REQUIRED`；已针对离线安全处理流水线、图片配额预算、缓存撤销与切信竞态、服务端唯一发件人验证及数据库唯一索引、识别范围包含协议相对路径、规范化算法分离与碰撞降级、单信深色覆盖提升至应用级 `mailStore` 解决跨路由卸载丢失、WebKit 与真实 PostgreSQL/Cookie 全栈验证完成全面修订。

### 有意不测

- 第三方广告拦截插件对图片的拦截：不受应用控制，使用本地测试图片服务器验证应用自身行为。
- 缺少 Content-ID 且无法唯一对应附件的非标 cid 图片：保持原样，不做猜测性映射。
- 域名级与全局放行：未定义产品语义，本 task 不覆盖。

### 测试策略

- 后端 PostgreSQL 集成测试：两类放行记录的写入、并发重复写入唯一约束与幂等、大小写与空白规范化真值表、跨账号全局命中、详情标志计算、非法/控制字符/CRLF 发件人拒绝、邮件删除级联与发件人白名单独立保留；迁移升级与降级。
- 后端 API 契约测试：`AttachmentOut` 暴露 `content_id`；新放行接口状态码与 OpenAPI 生成一致性；无认证写请求拒绝，Cookie 会话缺失或错误 CSRF 拒绝，合法 API Key 保持免 CSRF。
- 前端离线安全流水线与组件测试：
    - 离线 DOM 容器与 DOMPurify 净化执行时序验证；
    - 恶意 CID、引号注入、事件属性、伪造 MIME 及非图片类型内联附件拦截降级测试；
    - 放行前父页面与子 iframe 外部网络请求计数（断言必须为零）；
    - 资源预算超限（单张正文内联图片 >10 MiB、单邮件累计 >20 MiB）、拉取超时、404/401 降级测试；
    - 切信与卸载触发 `AbortController.abort` 验证；
    - 缓存撤销与在途响应废弃、单封放行独立保留测试；
    - `viewModeOverride` 在 `mailStore` 中的切信与设置页往返保留测试。
- Playwright E2E（Chromium + WebKit 双浏览器）：
    - 真实全栈（PostgreSQL + FastAPI + 真实 Cookie 会话）；
    - 用可控测试图片服务器统计请求并确认图片成功解码（`naturalWidth > 0`），验证点击前无请求、点击后发起请求且可见，刷新后不重复拦截；
    - 发件人白名单对同发件人第二封邮件及另一账号邮件生效；
    - 撤销白名单后重新打开缓存邮件立即恢复拦截；
    - 含 `cid:` 正文内联图邮件在未放行远程图片时即正常解码显示（`naturalWidth > 0`），普通文件附件绝不发起自动请求。

### 风险与回退

- 风险：大体积正文内联图片在转为 data URL 注入时可能引起正文 DOM 内存占用升高；本 spec 已引入单张正文内联图片 ≤10 MiB、单邮件累计 ≤20 MiB、最多 3 并发、超时 5s 的严格预算约束，超限即安全降级为正文占位（附件列表仍保留手动下载），且切信即时 abort 请求并释放内存。普通文件附件不受此配额约束，保持点击后下载。
- 风险：已有用户此前在浏览器会话内临时放行的邮件在本变更后需要重新放行一次；属于预期的语义升级。
- 风险：历史未存储 Content-ID 的老邮件无法按 ID 匹配；保持安全降级原样。
- 风险：发件人地址规范化与展示不一致；由服务端收敛负责标准邮箱校验与规范化，客户端优先提交邮件 UUID。
- 风险：撤销白名单后未使已缓存详情失效，staleTime 内继续放行；以撤销即时阻断在途响应与重新校验测试覆盖。
- 风险：放行 API 尚未确认持久化就乐观放开图片，失败后远程请求已泄露访问事实；以失败分支的请求计数测试覆盖。
- 回退：撤销发布后执行迁移降级删除两张新增表即可；`AttachmentOut` 字段向后兼容，不改动既有数据；降级将清除已保存的用户放行偏好，邮件本体不受影响。

### 依赖与约束

- 需要新增 Alembic 迁移与重新生成 OpenAPI TypeScript 契约。
- 不引入新的第三方依赖；沿用现有认证、CSRF 与 PostgreSQL 事务设施。
- 放行记录属于隐私边界变更：只有用户显式操作且服务端持久化成功后才写入并放开图片，默认拦截行为与 CSP/sandbox 基线不得放宽。
- 内联图片注入严禁放宽沙箱基线（`d002`）。
