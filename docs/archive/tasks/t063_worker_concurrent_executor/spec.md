# Task spec

## 背景

p063 根因 2：用户点击「同步正文」入队 priority=10 的即时归档任务，却要等前面已认领的任务逐个跑完。核实（2026-10-30）结论比 p063 描述更根本：

- Worker 是单线程串行执行器。`_tick` 一次认领 `worker_claim_batch=5` 个任务，在同一线程内 for 循环逐个执行；执行期间不认领新任务。任何长任务（如 p063 中逐条推送 5 条已读耗时 69 秒的远程写回）都会阻塞其后所有任务，包括用户即时操作。
- 系统其余部分早已按并发设计：`claim_jobs` 使用 `SKIP LOCKED`；`AccountSyncLease` + fencing 保证同账号同步与写回互斥；`connection_slots` 提供全局 8 条供应商并发连接预算，后台批量归档只能用槽位 2–7，槽位 0–1 永久留给交互、元数据与写回流量（commit `2107c33f`、修复设计 R11 §7，t058 收入集中配置 `MAIL_CORE_TOTAL_SLOTS` / `MAIL_CORE_BACKGROUND_START_SLOT`）。但串行执行器同一时刻至多占用 1 个槽位，「8 槽预算」与「前台保留 2 槽」在单 Worker 进程内从未生效。
- 账号规模约 100、规划近千（t061 用户确认），串行执行器下一个慢账号的登录或长任务会拖慢全部账号。
- `acquire_lease` 对同一 `owner_id` 可重入并递增 fencing（`leases.py`），若同进程多个执行线程共用 `worker_id` 作为租约 owner，会互相顶掉 fencing；归档认领 `claimed_by` 同样以 `worker_id` 标识。
- t061 的全文件夹 STATUS 巡检在 Worker 主循环内同步执行网络探测，执行期间同样不认领任务。

参考实现（2026-10-30 源码核查）：Mailspring 每账号前台、后台两个独立 IMAP 会话线程，用户任务与按需拉正文走前台，不受后台同步阻塞；Thunderbird 每服务器缓存最多 5 条已登录连接并发服务操作。kkmail 单 Worker 服务数百账号，对应形态为「全局执行池 + 为前台流量预留容量」，与既有连接槽 8/6 模型一致。

## 契约区

### 范围

- Worker 执行模型由串行改为并发：执行位数量等于 `total_slots`；执行位空闲即按既有优先级顺序（`priority` 升序、`created_at` 升序）认领一个任务，任务结束即释放执行位并立即尝试下一次认领。
- 流量类别准入与连接槽一致：后台批量归档（`traffic_class_for_job` 判定为 background 的任务）同时在途数不超过 `total_slots - background_start_slot`；达到上限时认领跳过此类任务，其余执行位留给前台任务。
- 同账号租约任务认领期互斥：需要账号租约的任务类型（`sync_account_folders`、`sync_folder_metadata`、`sync_folder_delta`、`reconcile_folder`、`remote_operation_push`）在同一账号已有同类任务处于 CLAIMED 时不被认领；不同账号并行；不走租约的归档任务可与同账号租约任务并行。互斥在认领查询中判定，跨进程同样有效。
- owner 标识细化到单次执行：账号租约、归档认领等以 owner 标识的资源，使用区分到单次任务执行的 owner，同进程并发执行互不覆盖；任务认领本身（`locked_by`）仍为 Worker 标识。
- 认领心跳统一：一个心跳线程为全部在途任务续期认领时间戳，替代每轮 tick 独立心跳线程。
- 周期性工作（回收、周期调度、t061 巡检探测）不阻塞任务认领与执行。
- 优雅停机：收到停止请求后不再认领新任务，在既有停机超时内等待在途任务结束；超时未结束的任务保持 CLAIMED，由既有回收机制接管。
- 移除 `worker_claim_batch` 配置项及其环境变量 `MAIL_CORE_CLAIM_BATCH`（含桌面端 sidecar 透传白名单），不新增执行位数量配置项。
- 审计并修正并发执行下的模块级可变状态线程安全（如 `blobs/quota.py` 的 `_dir_size_cache`）。
- 内嵌模式（API 进程内 Worker 线程）与独立 Worker 进程两种部署行为一致。

### 非范围

- 不改连接槽预算数值与 8/6 分配规则；不改任务优先级数值。
- 不实现多 Worker 副本间的执行位协调（当前部署为单 Worker 进程）；该约束写入 `decisions.md`。
- 不改远程写回实现（属 t064）与唤醒机制（属 t062）。
- 不改 IDLE watcher 独立配额与其线程模型。

- [ ] AC-001：存在至少 `total_slots` 个不同账号的可执行前台任务时，同一 Worker 内同时执行的任务数达到 `total_slots`，且任何时刻不超过 `total_slots`。
- [ ] AC-002：存在大量可执行后台批量归档任务时，同时执行的后台归档任务数不超过 `total_slots - background_start_slot`。
- [ ] AC-003：后台归档已达在途上限且均为长任务时，新入队的 priority=10 即时正文归档任务在 1 秒内开始执行，无需等待任何在途任务结束。
- [ ] AC-004：执行位空闲时，优先认领优先级数值最小的可执行任务；同优先级按入队先后。
- [ ] AC-005：同一账号的两个租约类任务不会同时处于执行中；该场景下不产生 `lease_busy` 结果；不同账号的租约类任务并行执行；同账号的租约类任务与即时正文归档可并行执行。
- [ ] AC-006：同一 Worker 内并发执行的任务不会使彼此的账号租约 fencing 失效或释放彼此的归档认领。
- [ ] AC-007：执行时长超过认领回收阈值的在途任务，在执行期间不被回收；Worker 进程被杀后，其在途任务由既有回收机制恢复为可认领。
- [ ] AC-008：某个在途任务抛出未捕获异常时，只有该任务按既有语义记为失败或重试，其他在途任务继续执行且结果正常落库。
- [ ] AC-009：周期调度或巡检探测执行期间，新入队的前台任务仍在 1 秒内开始执行。
- [ ] AC-010：停止请求后 Worker 不再认领新任务；在途任务在停机超时内结束的正常落库；超时未结束的任务保持 CLAIMED 并可被回收。
- [ ] AC-011：配置模型不再包含 `worker_claim_batch`；桌面端不再向 sidecar 透传 `MAIL_CORE_CLAIM_BATCH`。
- [ ] AC-012：内嵌 Worker 模式与独立 Worker 进程模式下 AC-001 至 AC-010 行为一致。
- [ ] [deploy] AC-013：真实账号环境中，在后台同步与归档持续运行时点击一封正文未归档的新邮件，Worker 日志显示该即时归档任务从入队到开始执行间隔不超过 2 秒。

- 单元测试：可控阻塞的 fake handler 统计并发峰值、前后台在途数、认领顺序；注入异常验证隔离；停止事件验证停机语义。
- PostgreSQL 集成测试：真实认领查询验证同账号租约任务互斥、跨「进程」（两个独立认领会话）互斥；并发执行下租约 fencing 与归档认领互不干扰；心跳与回收阈值。
- 配置与桌面端：配置模型与 `startup.js` sidecar 白名单测试同步更新（旧测试整体删除并写明理由，新增覆盖新语义的测试）。

### 风险与回退

- 风险：遗漏的线程不安全共享状态在并发下出现竞态；同进程 owner 混用导致租约或归档认领互相覆盖；DB 连接池容量不足以支撑 `total_slots` 个并发任务会话加控制连接；并发后单账号连接数上升触发服务商限流。
- 防御：模块级状态审计清单写入实施笔记；AC-006 专项覆盖 owner；核对 DB 连接池参数与执行位数量匹配；同账号租约任务互斥使单账号并发连接至多为 1 个租约任务 + 归档任务。
- 回退：git revert 本 task commit 恢复串行执行器与 `worker_claim_batch`。

### 依赖与约束

- 依赖 t062（任务通道唤醒，同改 `src/mail_core/worker/main.py`）。
- 与 t064 无文件级强冲突；本 task 只在 `worker/handlers.py` 调用点调整传入的 owner，不改 `sync/remote_push.py` 内部逻辑。
- 当前部署为单 Worker 进程；多 Worker 副本需改为「先取连接槽再认领」，本 task 只记录约束。
