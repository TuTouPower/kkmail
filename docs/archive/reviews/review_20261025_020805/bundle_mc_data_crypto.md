## Strengths

- Blob crypto (blobs/crypto.py): chunked AES-256-GCM with per-frame nonce derivation, final-flag in AAD (truncation/reorder detectable), random nonce prefix per blob, and fail-closed key loading with no dev fallback — matches spec and test_blob_keyring_required.
- Credential storage: AES-256-GCM with the credential_ref as AAD (ciphertext bound to ref, tested in test_credential_store_db.py:48), HKDF domain separation from blob keys, advisory-lock + row-lock serialization in credential_edit.
- OAuth: PKCE S256, state bound to a hashed session key + session_epoch, one-time state and one-time authorization-code claim under advisory locks, token_uri host allowlist, Microsoft tenant regex + identity re-verification against /me and mailbox, device-code polling driven server-side under the flow lock with slow_down handling.
- Backup (create/verify side): pg_dump failure raises by default — `allow_stub` defaults False everywhere in production paths and `verify_backup_package` rejects `sql_stub` members, so the previously suspected "stub seals as success" bug does NOT exist on the create/verify path; PGPASSWORD (never argv), outer kkbak checksum verified before decrypt, tar member allowlists with symlink rejection, 0600/0700 workspace hygiene.
- pg_dump stub re-verification (task prompt): confirmed fixed for create/verify; only restore's own stub check is dead code (see Medium finding at package.py:762), mitigated today by restore calling verify first.
- GC: two-phase delete (DB commit before unlink), post-commit re-check under digest lock, fail-closed on DB errors in unlink_gc_paths — matches spec AC-006 of mail_sync_and_storage.
- Auth: bcrypt, fail-closed DB credential fetch, session epoch revocation, login limiter keyed on socket peer (not X-Forwarded-For).

## Spec compliance

- docs/specs/auth_and_session.md AC-001..AC-005: implemented as specified (bcrypt, epoch in cookie, 10 failures/300s limiter, atomic password change with epoch increment, CSRF on mutations enforced at API layer).
